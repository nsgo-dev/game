# 命令行

`game` 是游戏层的命令行工具：一个命令，由子命令打包精灵图集、转换音频、生成资源清单、编码纹理、打开场景编辑器、构建发布包、无界面回放输入录像、对照存储的基线检查基准测试、创建项目、运行游戏并热重载资源，以及检查游戏的场景、地图和图集。子命令的调用方式一致：参数标志写在位置参数之前，读取的内容用 `-in`，写出的内容用 `-out`，帮助也一样。

## 安装

把命令作为工具加入你的模块，然后用 `go tool game` 运行：

```sh
go get -tool github.com/nsgo-dev/game/packages/game/cmd/game
go tool game help
```

`go.mod` 里的 `tool` 一行把命令固定在模块所用的游戏层版本上，参与这个游戏的每个人运行的都是同一个命令。用 [`game new`](#new) 创建的项目已经包含这一行。

## 命令

| 命令 | 作用 |
| --- | --- |
| `pack` | 把一个文件夹的 PNG 图片打包成精灵图集页面和供 `sprite.LoadAtlas` 读取的 TexturePacker JSON-hash 元数据 |
| `audio` | 对 WAV 文件做归一化、重采样，并转换为 WAV、AAC 或 MP3 |
| `manifest` | 从资源目录生成带类型的 Go 资源清单，缺少资源时构建失败 |
| `tex` | 把 PNG 或 JPEG 纹理编码为 BC1、BC3、ETC2 或 RGBA8 格式的 KTX2 容器，可选生成 mipmap |
| `editor` | 在场景编辑器中打开一个项目或 YAML 场景，未指定时打开演示场景 |
| `release` | 通过一次 `nsgo build` 为 macOS、Windows、Linux、Web、iOS 和 Android，或为 `game.yaml` 的导出预设，构建游戏的发布包 |
| `replay` | 检查各目录下的输入录像，并通过它们的回放测试无界面回放，结果不一致时失败 |
| `bench` | 无界面运行基准测试，有一项退化超过存储的基线时失败，或者更新基线 |
| `new` | 从模板在一个目录中创建游戏项目，其 `go.mod` 依赖游戏层，并包含 `game` 和 `nsgo` 工具 |
| `dev` | 用 `nsgo dev` 运行游戏，资源保存后在运行中的游戏里重新加载 |
| `check` | 检查一个目录下的场景、Tiled 和 LDtk 地图、精灵图集以及它们引用的文件，每个问题都报告所在的文件和行 |
| `help` | 列出所有命令，或显示某个命令的参数 |

`go tool game help` 列出所有命令，`go tool game help <command>` 或 `go tool game <command> -h` 显示一个命令的用法行、作用和参数。

命令成功或显示帮助时退出码为 0；执行失败（读不到文件、找不到编码器、清单已过期、构建失败、回放的结束状态不一致、基准测试退化、`check` 发现了失效的引用）时为 1；调用方式有误（未知参数、缺少必需参数、互相冲突的参数、多余的位置参数）时为 2，并同时打印该命令的用法。错误信息以命令名开头，例如 `game pack: -in directory is required`；未知或格式错误的参数例外，由 Go 的 flag 包用它自己的措辞报告，例如 `flag provided but not defined: -nope`。未知命令同样以 2 退出，但不打印用法，而是提示运行 `game help`。

### pack

```sh
go tool game pack -in art/ui -out assets -name ui -padding 2
```

把 `ui.png` 和 `ui.json` 写到 `-out`（帧放不下一页时改为 `ui-0.png`、`ui-0.json`、`ui-1.png` 等），并逐行打印路径。`-padding` 和 `-extrude` 设置每帧四周的透明间隔和重复的边缘像素，`-max-width` 和 `-max-height` 限制单页尺寸，`-scale` 写入 `meta.scale`，默认裁掉透明边框并记录每帧在未裁剪尺寸中的偏移，`-trim=false` 时保留边框。

### audio

```sh
go tool game audio -in sfx/jump.wav -out assets/jump.wav -rate 22050 -channels 1 -peak-db -1
go tool game audio -in music/theme.wav -out assets/theme.m4a -format aac -rms-db -14 -bitrate 192
```

读取 WAV 文件，重采样到 `-rate`，混合为 `-channels` 个声道，并按峰值（`-peak-db`）或响度（`-rms-db`，带软削波）归一化，两者只能选一，同时指定属于调用方式有误。WAV 输出由 Go 编写；MP3 需要 `PATH` 上有 `ffmpeg`，AAC 使用 `ffmpeg`，在 macOS 上缺少 `ffmpeg` 时改用 `afconvert`；都没有时报错并指出缺少的编码器。

### manifest

```sh
go tool game manifest -in assets -out assets/manifest_gen.go -pkg assets
go tool game manifest -in assets -out assets/manifest_gen.go -pkg assets -check
```

为 `-in` 下的每个资源写出一个带类型引用的 Go 文件，`-out` 为空时打印到标准输出。`-embed` 生成 `//go:embed` 指令而不是 `asset:` URI，`-embed-dir` 加在这些指令的模式之前。`-check` 不修改 `-out`，只在它与将要生成的内容不同时失败，供 CI 使用；用一行 `go:generate` 运行第一种写法即可让文件保持最新。生成文件的头部注明写出它的命令（`// Code generated by game manifest. DO NOT EDIT.`），因此由旧的 `gamemanifest` 命令生成的清单需要重新生成一次，`-check` 才会通过。

### tex

```sh
go tool game tex -format bc1 -mipmaps -srgb -out assets/albedo.ktx2 art/albedo.png
```

把位置参数（或 `-in`）指定的图片编码为 `-out`（简写 `-o`）处的 KTX2 文件，默认路径是输入路径换成 `.ktx2` 扩展名。`-format` 可选 `bc1`、`bc3`、`etc2` 或 `rgba8`，`-mipmaps` 写出直到 1x1 的完整 mipmap 链，`-srgb` 把纹理标为 sRGB，并在线性光空间中过滤 mipmap。

### editor

```sh
go tool game editor scenes/level1.yaml
go tool game editor .
```

在窗口中用 NSGo 场景编辑器打开指定的场景文件，未指定时打开一个小型演示房间。指定目录或 `game.yaml` 时打开游戏的[项目文件](project.md)及其主场景。场景格式见[编辑器与场景格式](editor.md)。

### release

```sh
go tool game release
go tool game release -channel store -release-notes notes/0.2.0.md
go tool game release -target macos_arm64,web -output build -dry-run
```

在指定目录（默认是当前目录，其中有游戏的 `nsgo.yaml`）里，通过一次 `nsgo build` 为所有平台构建游戏：未另行指定时，构建两种架构的 macOS、Windows 和 Linux，以及 Web、iOS 和 arm64 的 Android。每个目标的包写到 `<output>/<name>-<version>-<target>`，发布时上传的文件（磁盘映像、安装程序、Debian 和 Arch 包、AppImage、IPA、APK 和网站的 zip，各带一个 `.sha256`）写到 `<output>/releases`，目录结构与 `nsgo build` 相同。任一目标失败都会终止本次运行，退出码为 1。游戏的模块必须把 NSGo 作为工具（`go.mod` 里有 `tool github.com/nsgo-dev/nsgo/cmd/nsgo`，起始模板已带上），因为命令运行的是 `go -C <dir> tool nsgo build`，构建使用模块自己的 NSGo 版本；`-dry-run` 只打印这条命令而不运行。

目标取自 `-target`；没有时取 `nsgo.yaml` 旁边 `game.yaml` 的 `export` 预设，按顺序，没有 `targets` 的预设构建其平台名；再没有时取上面的六个平台，但渠道（`-channel`，没有时取 `nsgo.yaml` 的 `updates.channel`）为 `steam` 时只取 macOS、Windows 和 Linux，因为 `nsgo build` 只用桌面目标制作 Steam depot。命令不使用 `nsgo.yaml` 的 `build.targets`：它是日常直接运行 `nsgo build` 时的目标列表，起始模板里的这份包含模拟器构建、不含 Linux，所以发布用的目标列表应写在预设里。输出目录取自 `-output`；没有时取 `game.yaml` 的 `export.output`；再没有时取 `nsgo.yaml` 的 `build.output`：

```yaml
version: 1
export:
  output: dist
  presets:
    - platform: macos
    - platform: windows
      targets: [windows_x64]
    - platform: linux
    - platform: web
    - platform: ios
    - platform: android
```

命令只读取 `game.yaml` 的 `version`（必须是整数 1）和 `export` 部分。它拒绝项目文件字段（`version`、`name`、`id`、`appVersion`、`window`、`display`、`input`、`audio`、`autoload` 和 `export`）以外的顶层字段，因此拼错的 `export` 不会被悄悄跳过；在 `export` 里则拒绝未知字段、空的 `presets` 列表、未知的平台和目标、属于其他平台的目标、重复项以及位于项目之外的输出目录；文件的其余部分归项目文件管理。`-channel` 即 `nsgo build` 的同名参数：`store` 构建商店接受的包（Mac App Store 安装包，同时构建两种 macOS 架构时为通用包，以及 Windows MSIX、Flatpak 包和 Android App Bundle），取代直接分发的磁盘映像、安装程序和 APK；`-release-notes` 和 `-jobs` 也原样传给它。签名、公证和上传商店遵循 `nsgo.yaml` 和 `nsgo publish`。

一台机器能构建哪些目标，以 `nsgo doctor` 的显示为准：iOS 需要装有 Xcode 的 Mac，macOS 磁盘映像需要在已登录的会话里运行 `hdiutil`，所以为所有平台发布要在 Mac 上运行。

### replay

```sh
go tool game replay ./...
go tool game replay -run '^TestBossReplay$' ./levels
```

无界面回放游戏的[输入录像](replay.md)，供 CI 使用。录像要靠游戏自己的模拟才能回放，所以命令通过游戏的测试来回放：它先加载各目录下的每个 `*.replay.yaml` 文件，只要有一个无法回放（未知的键、表头中没有的名字、乱序的步），或者某个目录里一个录像也没有，就直接失败而不运行任何测试，这样写错的路径不会蒙混通过。随后用 `go tool nsgo test` 无界面运行名字匹配 `-run` 的测试，默认是名字中含 `Replay` 的所有测试，有一个失败命令就失败；一次回放的结束状态与测试期望的不同时，`replay.AssertEndState` 正是让测试失败。某个目录里没有任何测试通过时命令也会失败，例如 `-run` 一个测试也没匹配到，这样命名不对的测试或写错的模式不会在一个录像也没回放的情况下蒙混通过。请据此给回放录像的测试命名，例如 `TestLevel1ClearReplay`。

每个目录都按 `nsgo test` 的方式当作一棵树：无论末尾有没有 `/...`，其子目录都会被搜索和测试，跳过名字以 `.` 或 `_` 开头的目录和嵌套模块，但不跳过 `testdata`。默认是 `./...`。命令会运行 `go tool nsgo`，因此模块需要像 NSGo 应用那样把 NSGo 的命令加为工具。

### bench

```sh
go tool game bench ./sprite ./tilemap
go tool game bench -update ./sprite ./tilemap
go tool game bench -in bench.txt
```

用 `go tool nsgo test -bench` 无界面运行各目录下的基准测试，共运行 `-count` 次（默认 3 次），每次运行 `-benchtime`（默认 200ms），取每个基准测试每次操作的耗时、字节数和分配次数的中位数，与 `-baseline` 指定的基线文件比较，默认是 `benchmarks/baseline.yaml`。它为基线中的每个基准测试打印一行，有一项超过限度或者没有测到，或者基线中没有任何基准测试时失败；测到了但基线中没有的基准测试列为新增，不算失败。`-bench` 像 `go test -bench` 那样缩小运行的范围。`-in` 从一个 `go test -bench -benchmem` 输出文件读取结果，不运行任何东西。

`-update` 改为把测得的中位数写入基线，基线不存在时创建它，并保留这次没有测到的基准测试。基线是 YAML 文本文件，可以像其他文件一样审阅和编辑：格式版本、一段备注、各项指标允许退化的百分比，以及按名字排序、每个基准测试一行。加载后再保存不会改变它，未知的键和缺少的指标会被拒绝。

```yaml
version: 1
note: Update with go tool game bench -update ./sprite ./tilemap
max_regression_pct: {ns_per_op: 25, bytes_per_op: 25, allocs_per_op: 25}
benchmarks:
  BenchmarkBatchDraw1000: {ns_per_op: 155412, bytes_per_op: 72232, allocs_per_op: 754}
  BenchmarkRaycast: {ns_per_op: 827.3, bytes_per_op: 0, allocs_per_op: 0}
```

基准测试的名字不带 `-GOMAXPROCS` 后缀，因此在一台机器上记录的基线可以在另一台机器上读取，但每次操作的耗时取决于机器：请在 CI 检查基线所用的同类机器上记录它。这个格式由 `tooling/bench` 包读写。

### new

```sh
go run github.com/nsgo-dev/game/packages/game/cmd/game@latest new mygame
go tool game new -name "Space Rocks" -module example.com/rocks rocks
```

把起手模板（即 `template/template` 中、`nsgo init -template github.com/nsgo-dev/game/template` 写出的那个项目）写入指定目录，目录不存在时会创建，并打印每个文件的路径。随后在该目录运行 `go get -tool github.com/nsgo-dev/game/packages/game/cmd/game@<version>` 和 `go mod tidy`，这两步需要访问 Go 模块代理。这样项目依赖该版本的游戏层，`game` 工具与 `nsgo` 工具并列，无需修改即可用 `go tool nsgo dev` 构建运行。

游戏名称默认取目录名，`-name` 可以另行指定（字母、数字、空格、`-` 和 `_`，以字母开头）。名称写入 `game.yaml` 和 `nsgo.yaml` 的 `name`，`id` 由它派生为 `dev.nsgo.<去掉空格和标点的小写名称>`。模块路径默认是小写名称、单词之间用 `-` 连接，`-module` 可以另行指定。与标准库包同名的模块路径（例如名为 Time 的游戏得到的 `time`）会被拒绝，因为这样的项目无法构建，此时需要用 `-module` 指定，例如 `-module example.com/time`。`-version` 是要依赖的游戏层版本，例如 `v0.4.0`、某个提交或 `latest`；默认是正在运行的命令自身的版本，所以 `go run …@v0.4.0 new` 创建的项目使用 `v0.4.0`，而从本仓库的检出构建的命令则使用 `latest`。`-template` 选择模板，目前只有 `starter`。

只要目录中已经存在任何一个将要写入的文件，`new` 就什么也不写，并以 1 退出。`go get` 或 `go mod tidy` 失败时（例如没有网络），已写入的文件会保留，错误信息会列出还需在该目录运行的命令以完成项目：`go get` 失败时是 `go get -tool …` 和 `go mod tidy` 两条，`go mod tidy` 失败时只有它一条。

### dev

```sh
go tool game dev
go tool game dev -target native -fps
go tool game dev ./mygame -lang fr
```

运行 `go tool nsgo dev`：它构建游戏、启动游戏，并在 Go 代码改动时重新构建；同时把资源所在位置告诉运行中的游戏，即 `-assets` 的绝对路径（默认是项目目录下的 `resources`），放在环境变量 `NSGO_GAME_ASSETS` 里，`hotreload.DevAssetsDir` 返回的就是它。它必须是游戏的 `assets.Manager` 读取 `"asset:"` URI 的目录：用 `assets.WithFS(os.DirFS(hotreload.DevAssetsDir()))` 创建的 Manager，因为没有 `WithFS` 的 `Manager` 读取的是运行 `game dev` 的目录下的 `assets/`。游戏用 `hotreload.NewDevWatcher` 在这个目录上启动监视器后，它已加载的图集、图片或数据文件在保存后一秒内就会在游戏里更新，无需重启；见[保存时重新加载](assets.md#保存时重新加载)。第一个不是参数标志的位置参数是项目目录，省略时为 `.`，其后的参数原样传给 `nsgo dev`；`-target` 和 `-fps` 也会传过去；目录之后的参数里如果有 `-target`，就以它为准，与 `nsgo dev` 的处理一致。`nsgo dev` 的输出就是 game dev 的输出，Control+C 会同时停止两者。`nsgo dev` 失败时 `go tool game dev` 以 1 退出。

资源在 `native` 和 `tui` 目标上重新加载，带 `-android-host` 的 `android` 目标也可以，这些目标的应用的 Go 代码运行在本机并读取这些文件。在网页和手机上，应用访问不到资源目录，game dev 会提示这一点，游戏要等 `nsgo dev` 重新构建后才拿到资源改动。没有资源目录时，game dev 照常运行 `nsgo dev`，并提示资源不会重新加载。游戏用 `go:embed` 嵌入的资源属于二进制的一部分：这类文件改动时 `nsgo dev` 会重新构建并重启游戏，而监视器的重新加载会在那之前先显示改动。

### check

```sh
go tool game check
go tool game check examples/caverun
```

检查所指目录（或 `-in`；两者都没给时为工作目录）下的每个场景、地图、图块集和图集，以及它们之间的引用，让失效的引用在玩家碰到之前就报错。每个问题以 `file:line: message` 的形式打印到标准错误，文件名从工作目录算起，编辑器可以直接打开，最后打印问题数，命令以 1 退出；没有问题时打印每类文件各检查了多少个，以 0 退出：

```text
examples/caverun/assets/level1.tmj:1397: tileset image "tileset.png": not found
game check: 1 problem
```

| 文件 | 检查内容 |
| --- | --- |
| 场景（`*.scene.yaml`、`*.scene.yml`） | 按[场景格式](editor.md)解析并校验通过，没有未知字段；瓦片地图的 `source` 是存在且检查通过的 Tiled `.tmj` 地图；每个精灵的 `atlas` 存在且含有它的 `frame`；内联瓦片地图的 `tileset` 图集含有它用到的每个瓦片 ID 的帧；`material` 文件存在、是有效的材质，且它的 `texture` 存在 |
| Tiled 地图（`.tmj`）和图块集（`.tsj`） | 外部图块集是存在的 JSON 图块集（`.tsj`，或旧版 Tiled 使用的 `.json`；不是 `.tsx`）；图块集图片和图像图层的图片存在，组图层里的也算；地图能用 `tilemap.LoadTiled` 加载 |
| LDtk 项目（`.ldtk`） | 图块集图片和关卡背景存在；没有关卡保存在单独的 `.ldtkl` 文件中，因为 `tilemap.LoadLDtkAll` 不读取这些文件（在 LDtk 中关闭“Save levels to separate files”）；项目能用 `tilemap.LoadLDtkAll` 加载 |
| 精灵图集（顶层有 `frames` 和 `meta` 的 JSON，即 TexturePacker 和 Aseprite 导出的格式） | `meta.image` 存在；每一帧都落在图片之内；图集能用 `sprite.LoadAtlas` 加载 |

地图、图块集和图集里写的路径相对于该文件本身，与 Tiled、LDtk 和纹理打包工具的写法一致。场景的瓦片地图 `source` 和 `material`，以及材质的 `texture`，相对于项目根目录：从场景往上最近一个含有 `nsgo.yaml` 或 `go.mod` 的目录，都没有时为被检查的目录。场景按游戏的 `sceneformat.AssetResolver` 的方式用名字指代图集，所以检查按文件名找它：同一项目中去掉 `.json` 后的文件名等于这个名字的图集 JSON（`actors` 即 `art/actors.json`），或者从项目根目录算起的路径等于这个名字的（`art/actors`）。有多个匹配时取离场景最近的一个，距离按从场景往上走到共同目录、再往下走到图集所经过的目录数计算，所以场景旁边的图集优先于子目录里的；两个同样近时报告为有歧义，直到场景用路径指明其中一个。没有图集匹配、但有同名的 JSON 文件无法解析或不是图集时，报告该文件的问题。路径必须是相对路径、使用正斜杠，且不能指到被检查的目录之外。PNG、JPEG 和 GIF 图片必须能解码；其他图片只要存在即可。

名字以 `.` 或 `_` 开头的目录以及名为 `testdata` 的目录会被跳过，与 go 命令的做法一致。其他 JSON 和 YAML 文件不会被读取。地图或图集的加载器报告的问题不带行号，因此打印为 `file: message`；只有当文件的引用都能解析时，检查才会运行这个加载器，同一个错误不会被报告两次。

Examples 工作流会对示例游戏运行 `game check`。要在自己游戏的 CI 中运行它，按上文把命令作为工具加入模块，然后在游戏目录下运行 `go tool game check`。这些检查也是一个包，`github.com/nsgo-dev/game/packages/game/tooling/assetcheck`，它的 `Check` 接受一个 `fs.FS`，以值的形式返回问题。
