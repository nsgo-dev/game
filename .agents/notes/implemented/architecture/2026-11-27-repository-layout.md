# Agent Note: Repository layout of the root module, cmd/, internal/, pkg/ groups, tools/ and template/

Status: implemented

## Problem

The repository holds one importable Go module (`github.com/nsgo-dev/game`), its binaries, nearly eighty top-level library packages, sixteen project templates, the examples, contributor tooling, a website, bilingual docs and design artboards. Without written placement rules, every new package or command lands wherever its author guesses: service daemons sit three levels deep under the library they serve (`pkg/accounts/cmd/accountsd`), sample games live inside library packages, contributor commands sit in `cmd/` next to the binaries users install, a package named `net` shadows the standard library, and a `tooling` directory holds both editor-only code and packages every release build links. A reader cannot tell from a path whether a directory is a public import path, a shipped binary, a repo-only tool or a fixture, and the stability table, the website catalog and the PR labels each grow their own exceptions.

## Decision

The Go module root is the repository root (`go.mod` declaring `module github.com/nsgo-dev/game`), so releases use plain `vX.Y.Z` tags and `go tool nsgo check` / `go tool nsgo test ./...` run from the root. Each top-level directory has one purpose, and the rules below decide where new code goes.

### Placement rules

- **Root package `game`**: `loop.go`, `doc.go` and the Loop's own tests only. It is the one importable package outside `pkg/`. Repo-wide checks never live in the root package.
- **`pkg/`**: every other importable library package, at `github.com/nsgo-dev/game/pkg/<name>`. A package that only refines another package nests under it: `ai/navbake`, `ai/navbake3d` and `ai/perception3d` under `pkg/ai`, `tilemap/tileshape` under `pkg/tilemap`.
- **`pkg/online/`**: the service and netcode packages (`accounts` and its stores, `achievements`, `cloudsave`, `leaderboard` and its `selfhost` service, `liveops`, `netplay`, `presence`, `server`). A package belongs here when nothing outside `pkg/online` imports it except the service daemons in `cmd/`, the examples and the `internal/repocheck` tests; `git grep` for `pkg/online/` imports outside the group checks this. The netcode package is named `netplay`, never `net`, so it does not shadow the standard library's `net`.
- **`pkg/tooling/`**: build, editor and dev-time tooling whose real code a release build never links. A package may compile to a release-tag stub (`//go:build release`, as `hotreload_release.go` and `devstate_release.go` do) and still belong here. A package whose real code a release build links (`ktx2`, `importsettings`, `datatable`, `jsonschema`) sits flat under `pkg/` instead.
- **Every other package stays flat under `pkg/`**, including the genre packages (`bullets`, `cards`, `fighting`, `idle`, `platformer`, `rhythm`, `rts`, `undo`, `vehicle`, `vn`) and shared building blocks such as `framedata`, `fog` and `rooms`.
- **`cmd/`**: only binaries the project ships to users: `game`, `nsgo-game` (names fixed by NSGo's extension lookup), `gameproject`, `sizecheck`, and the service daemons `accountsd`, `cloudsaved` and `leaderboardd`. The website catalog lists the daemons under the Online group (`ONLINE_CMDS` in `apps/website/plugins/site.ts`), not under the CLI tools.
- **`internal/`**: shared helpers that the root package, `cmd/*` and `pkg/*` all import (`formattest`, `gamecli`, `detmath` and so on), plus two fixtures: `internal/repocheck` holds the repo-wide conformance, formats, stability and skill tests (its `main_test.go` changes to the repository root before `nsgotest.Main`), and `internal/sizeprobe` is the `package main` that CI builds to measure release package sizes.
- **`tools/`**: one repo-only module, `github.com/nsgo-dev/game/tools` (`replace` to `..`), for contributor commands that users never install: `changelog`, `agenteval`, `gameschema`, `gameapi` and the `pixelfxref` node script. They are outside the stability table.
- **`template/`**: the sixteen project templates, each in its own Go module. `template/go.mod` declares `github.com/nsgo-dev/game/template`, whose default template is `template/template`, and every other template is `template/<name>/go.mod` with its files in `template/<name>/template/`. NSGo v0.3.4 `init_module.go` reads a template module's files from its `template/` directory, which fixes both the directory name and the nesting. `game new` writes the embedded copy under `internal/gamecli/_templates/projects`.
- **`examples/`**: one module per playable sample (`replace` to `../..`), all listed in `go.work`, including `dedicatedserver` and `vnsample`. A sample never lives inside a library package.
- **`docs/en` and `docs/zh`**: the published, localized pages only. **`design/`** sits outside `docs/` and holds contributor-facing material that is not localized, such as `design/editor`, the artboards `pkg/editor` implements.

### Contracts that follow from the layout

- Format IDs on `docs/{en,zh}/formats.md` (`<!-- format: online/accounts -->`, `ai/navbake`) are the package path relative to `pkg/`; `internal/formattest`, `internal/repocheck/formats_test.go` and `conformance_test.go` strip the `pkg/` prefix when matching packages to entries.
- `docs/{en,zh}/stability.md` and `skills/nsgo-game/references/packages.md` list packages relative to `github.com/nsgo-dev/` (`game`, `game/cmd/<name>`, `game/pkg/<name>`), and `apps/website` strips `pkg/` for the catalog groups and the API sidebar.
- `.github/labeler.yml` gives each flat package its own `pkg/<name>` label; a group directory takes one label for everything under it (`pkg/online` also covers the daemons and `examples/dedicatedserver`, `pkg/tooling` covers its subpackages), and nested packages share their parent's label.
- Website unit tests use the `*.spec.ts` suffix, so `bun test` finds them while `go tool nsgo test ./...` at the module root does not take them for NSGo TSX tests.

## Alternatives considered

1. **Keep the module in `packages/game` as a Go submodule**: the repository root stays minimal and no import rewrite is needed. Rejected because every release needs `packages/game/vX.Y.Z` submodule tags and every import path repeats `packages/game`.
2. **Flatten `pkg/<name>` into the module root**: gives the shortest import paths (`github.com/nsgo-dev/game/sprite`). Rejected because nearly eighty package directories would sit beside about fifteen non-Go trees (`apps`, `docs`, `design`, `library`, `skills`, `template`, `tools`) and clash in meaning (`library/` against `tooling/library`); "`pkg/` is the importable library" is the simpler rule. `packages/<name>` instead of `pkg/<name>` was weighed too and loses on length and Go convention.
3. **Group core, 3D or math packages (`pkg/core/sprite`, `pkg/3d`, `physics/physics3d`)**: a deeper tree looks more organized. Rejected because these segments carry no rule a reader can apply, `pkg/3d/render3d` stutters, and `physics3d` does not import `physics`.
4. **A `pkg/genre` group**: it would separate genre kits from engine packages. Rejected because no rule decides membership. Membership by dependency (imported only by templates) admits `undo` and `vehicle` while leaving out `framedata`, `fog` and `rooms`, which `pkg/debug`, `pkg/worldmap` and `pkg/editor` import from non-test code even though only one genre uses each. If a genre group is wanted later, membership must be by purpose, and `framedata` and `rooms` move with it.
5. **Serve every template from the root module** (`template/<name>` flattened, a `game/template` package embedding them, `nsgo init -template github.com/nsgo-dev/game#<name>`): it removes the sixteen template modules and the 365-file embedded copy under `internal/gamecli/_templates/projects`. Not adopted: `nsgo init` would then download the whole root module zip (about 21 MB of it `pkg/pixelfx` golden images) instead of a small template module, template creation would break between merge and the next tag because `go.mod.tmpl` must pin a release that does not exist yet, NSGo v0.3.4 has no default template for a `template/` directory of named templates (`init_module.go:70-74`), and every root `nsgo check` / `nsgo test ./...` would vet sixteen more `package main` programs for every target.
6. **Plural `templates/`**: reads better next to `examples/`. Rejected because NSGo v0.3.4 `init_module.go:40` hard-codes `template/`.
7. **`pkg/pixelfx` as its own module**: it would keep its 18 MB of golden PNGs out of the root module zip. Rejected for now because `internal/gamecli` imports `pixelfx` and `pixelfx` imports root packages, so the two modules would require each other; it is a module-boundary decision of its own.
8. **Separate modules for `gameschema` and `gameapi`, or `sizeprobe` under `tools/`**: smaller, independent tool modules. Rejected because one tools module is enough for repo-only commands, and `sizeprobe` must build and vet against the root module for every target, which `internal/` gives it.
9. **Other renames (`apps/website` to `website/`, `docs/<lang>/templates/*.md`, design files beside `pkg/editor`, renaming `benchmarks/`, moving `library/`, `internal/gamecli/_templates/generate` to `_generate`)**: rejected because none makes a path clearer, and several break contracts: the website's flat `rewriteLink` docs, the `pkg/*` changelog gate, the default path in `bench.go`, and the published raw URL of `library/index.yaml`.

## Consequences

- **Benefits**: a path says what a directory is (public import path, shipped binary, repo-only tool or fixture), and the placement rules decide where new code goes without a discussion. Releases use plain root tags. `cmd/` matches what users can `go install`, and the stability table, catalog and labels follow the same groups.
- **Costs**: import paths, module paths and command locations change for users: the daemons (`game/cmd/accountsd`, `cloudsaved`, `leaderboardd`), `pkg/online/*` and `netplay`, `pkg/ai/navbake*`, `pkg/tilemap/tileshape`, the promoted `ktx2`, `importsettings`, `datatable` and `jsonschema`, and `gameschema`, `gameapi` and `wasmprobe`, which are no longer public. Each is listed in `changelog.d`. The `netplay` rename changes identifiers that only the build catches, and docs mentions of `net.X` are checked by no test. A new `pkg/<name>` needs a labeler entry, and a new `pkg/tooling` or `pkg/online` package must satisfy its group's rule.
- **Kept on purpose**: sixteen template modules and the embedded copy under `internal/gamecli/_templates/projects` stay, with the duplication that implies (see alternative 5).
- **Open follow-ups**: `pkg/debug` shadows `runtime/debug`; `pkg/editor` is large enough to split; `cmd/gameproject` and `cmd/sizecheck` could fold into `game` subcommands; `pkg/pixelfx` may become its own module. Each is a change of its own, not a move.
- **Verification**: `go tool nsgo check`, `go tool nsgo test ./...` and `go tool nsgo test ./internal/repocheck` (formats, stability and conformance against the layout), the examples and templates CI jobs, `go run ./tools/changelog check`, `bun run verify-notes`, and the website's `bun run test`.
