# Agent Note: Repository layout of the root module, cmd/, internal/, pkg/ groups, the editor tree, tools/ and template/

Status: implemented

## Problem

The repository holds one importable Go module (`github.com/nsgo-dev/game`), its binaries, nearly eighty top-level library directories (about 150 packages with their subpackages), sixteen project templates, the examples, contributor tooling, a website, bilingual docs and design artboards. Without written placement rules, every new package or command lands wherever its author guesses: service daemons sit three levels deep under the library they serve, sample games live inside library packages, contributor commands sit in `cmd/` next to the binaries users install, a package named after a standard library package (`net`, `debug`, `token`) shadows it in every file that imports both, a package named for its implementation detail (`perf`, `effects`) mixes unrelated APIs, and a single-consumer helper sits in the root `internal/` where any tree may import it. A reader cannot tell from a path whether a directory is a public import path, a shipped binary, a repo-only tool or a fixture, and the stability table, the website catalog and the PR labels each grow their own exceptions.

## Decision

The Go module root is the repository root (`go.mod` declaring `module github.com/nsgo-dev/game`), so releases use plain `vX.Y.Z` tags and `go tool nsgo check` / `go tool nsgo test ./...` run from the root. Each top-level directory has one purpose, the rules below decide where new code goes and what it is called, and `internal/repocheck/catalog_test.go` enforces the parts a test can check.

### Placement rules

- **Root package `game`**: `loop.go`, `doc.go` and the Loop's own tests only. It is the one importable package outside `pkg/`. Repo-wide checks never live in the root package.
- **`pkg/`**: every other importable library package, at `github.com/nsgo-dev/game/pkg/<name>`. A package that only refines another package nests under it: `pathfind/navbake` under `pkg/pathfind`, `pathfind3d/navbake3d` under `pkg/pathfind3d`, `ai/cover3d` and `ai/perception3d` under `pkg/ai`, `tilemap/tileshape` under `pkg/tilemap`.
- **`pkg/online/`**: the service and netcode packages (`accounts` and its `authtoken`, `sqlstore`, `sqlitestore`, `pgstore` and `storetest`, `achievements`, `cloudsave` and its `sqlstore`, `sqlitestore` and `pgstore`, `gameserver`, `leaderboard` and its `selfhost` service, `liveops`, `netplay`, `presence`). A package belongs here when nothing outside `pkg/online` imports it except the service daemons in `cmd/`, the examples and the `internal/repocheck` tests; `git grep` for `pkg/online/` imports outside the group checks this. A store package that links an SQL driver holds exactly one driver (`sqlitestore` imports `modernc.org/sqlite`, `pgstore` imports `pgx`), and the driver-agnostic `sqlstore` takes a `*sql.DB` and a dialect, so a game that stores in SQLite never links Postgres.
- **`pkg/tooling/`**: build, editor and dev-time tooling whose real code a release build never links: `assetbuild`, `assetcheck`, `atlaspack`, `audioconv`, `bench`, `credits`, `devstate`, `gamedebug`, `hotreload`, `library`, `manifest`, `playtest`, `refs` and `sizecheck`. A package may compile to a release-tag stub (`//go:build release`, as `gamedebug`, `hotreload` and `devstate` do) and still belong here, so a template may import `pkg/tooling/gamedebug` and still ship a release build without it. A package whose real code a release build links (`ktx2`, `importsettings`, `datatable`, `jsonschema`) sits flat under `pkg/` instead.
- **`pkg/editor/`**: the editor is a product tree of its own, not a tooling package. `pkg/editor` is one package holding the `Editor` facade, because `Editor`'s methods cannot leave the type's package and the MCP rule is that every action is an exported `Editor` method. Its public subpackages are the pieces a caller outside the editor uses by name: `theme` (the design tokens, `theme.Palette`, `theme.Core()`), `keychain` (OS secret storage, `keychain.Store`, the type of the exported `Editor.Keychain` field), `editorcmd` and `editormcp`. A feature moves to `pkg/editor/internal/<feature>` only when its host surface is far smaller than the feature and needs no editor model types: the feature package never imports `pkg/editor`, the editor builds a `Host` struct of callbacks, and `Editor` keeps its public methods as forwarders and its public types as aliases. `internal/profiler` meets that bar; `remote*.go` stays in `pkg/editor` because its host would need `Doc`, `History` and the document's object IDs (see Consequences).
- **Every other package stays flat under `pkg/`**, including the genre packages (`bullets`, `cards`, `fighting`, `idle`, `platformer`, `rhythm`, `rts`, `undo`, `vehicle3d`, `vn`) and shared building blocks such as `framedata`, `fog`, `rooms`, `dialogue`, `mempool` and `spatial`.
- **`cmd/`**: only binaries the project ships to users: `game`, `nsgo-game` (names fixed by NSGo's extension lookup), `editor` (with its own `nsgo.yaml` and signed bundle), and the service daemons `accountsd`, `cloudsaved` and `leaderboardd`. A front end over one library is a `game` subcommand, not a binary of its own: `game size` drives `pkg/tooling/sizecheck` and `game project` drives `pkg/project` from `internal/gamecli`. The website catalog lists the daemons under the Online group (`ONLINE_CMDS` in `website/plugins/site.ts`), not under the CLI tools.
- **`internal/`**: helpers imported from two or more subtrees (`detmath`, `devimage`, `formattest`, `gamecli`, `jsonedit`, `loaderrtest`, `releaseplan`), repo-only libraries that the tools module imports (`apiref`, which `tools/gameapi` and `internal/repocheck` read; the internal rule is path-based, so `github.com/nsgo-dev/game/tools` may import it), and two fixtures: `internal/repocheck` holds the repo-wide catalog, conformance, formats, stability and skill tests (its `main_test.go` changes to the repository root before `nsgotest.Main`), and `internal/sizeprobe` is the `package main` that CI builds to measure release package sizes. A helper that one subtree uses lives in that subtree's `internal/` (`pkg/editor/internal/qrcode`, `pkg/placeholder/internal/samplegltf`).
- **Large test-only fixtures** sit in a `testdata/` directory that holds a stub `go.mod`, so the published module zip leaves them out, and the tests that read them skip when the directory is absent, as in a downloaded copy of the module: `pkg/render3d/testdata/damagedhelmet` and `pkg/pixelfx/testdata` (the 1683 golden PNGs under `testdata/ref/<category>/<effect>/`, located by `pixelfxtest` through `runtime.Caller`; `CheckEffect` fails when it compares zero frames, so a mis-wired path cannot pass as a skip).
- **Screenshot tests** live with the package they render: the editor's sit in `pkg/editor` as package `editor_test` (external test packages may import `editormcp` without a cycle), and only `autosave_screenshot_test.go`, which calls `editorcmd.New`, stays in `editorcmd`.
- **`tools/`**: one repo-only module, `github.com/nsgo-dev/game/tools` (`replace` to `..`), for contributor commands that users never install: `changelog`, `agenteval`, `gameschema`, `gameapi` and the `pixelfxref` node script. They are outside the stability table. A contributor tool's documentation is a `README.md` beside the tool (`tools/agenteval/README.md`, `tools/pixelfxref/README.md`), in English only, not a page under `docs/`.
- **`template/`**: the sixteen project templates, each in its own Go module. `template/go.mod` declares `github.com/nsgo-dev/game/template`, whose default template is `template/template`, and every other template is `template/<name>/go.mod` with its files in `template/<name>/template/`. NSGo v0.3.4 `init_module.go` reads a template module's files from its `template/` directory, which fixes both the directory name and the nesting. `game new` writes the embedded copy under `internal/gamecli/_templates/projects`.
- **`examples/`**: one module per playable sample (`replace` to `../..`), all listed in `go.work`, including `dedicatedserver` and `observatory`. A sample never lives inside a library package. An example is named for the game or the job it does, never for the package it demonstrates, and a game example's app ID is `dev.nsgo.game.examples.<dir>`, in the same `dev.nsgo.game` namespace as `cmd/editor` (`dev.nsgo.game.editor`). The tutorial chapters under `examples/tutorial` keep `dev.nsgo.starcatcher[.chNN]`, because they are the reader's own project as the `docs/*/tutorial-0N` pages write it.
- **`website/`**: the official site at the top level (the root `package.json` workspaces are `["website"]`).
- **`docs/en` and `docs/zh`**: the published, localized pages only, flat, one slug per page. **`design/`** sits outside `docs/` and holds contributor-facing material that is not localized, such as `design/editor`, the artboards `pkg/editor` implements.

### Naming rules

- **2D and 3D**: a package that only works in 3D carries the `3d` suffix (`vehicle3d`, `pathfind3d`, `navbake3d`, `cover3d`, `physics3d`, `render3d`); a package without a suffix is 2D or dimension-agnostic (`physics`, `scene`, `pathfind`, `navbake`). A 2D package does not take a `2d` suffix, and a 3D package whose name already says what it is (`anim3d`) keeps it.
- **No standard library names**: no package other than a `main` package shares its name with a standard library package (the last element of its import path), which would shadow it in every file that imports both. `TestNoStdPackageNames` enforces this, and its `stdNameExemptions` map is empty; an entry is allowed only with a reason and is refused once the clash is gone. The rule is why the netcode package is `netplay`, the debug overlay `gamedebug` and the token signer `authtoken`.
- **No names that read as something else**: a package name avoids common local variable names (`nav`, `pool`, `path`), NSGo concepts (`devtools`, which is NSGo's DevTools and `nsgo dev -devtools`) and names that mean another thing elsewhere in the repository (`pack`, which means an asset pack in `library` and `placeholder`, hence `atlaspack`). Where a short name is ambiguous, the `game` prefix disambiguates it, as `gameui`, `gametest`, `gameserver` and `gamedebug` do.
- **Identifier prefixes**: a prefix that only namespaced a group of identifiers inside a larger package goes once the group is a package of its own, so callers write `theme.Palette`, `dialogue.Runner` and `spatial.Hash`, not `theme.SpecPalette`, `dialogue.DialogueRunner` or `spatial.SpatialHash`. A prefix that is a term of art stays: `pathfind.NavMesh`, `NavAgent` and `PathOptions` keep their names, which also keeps them parallel to `pathfind3d`.

### Contracts that follow from the layout

- `internal/repocheck/catalog_test.go` keeps the catalogs complete: `TestLabelerCoversEveryPackage` requires a `pkg/<name>/**` glob in `.github/labeler.yml` for every directory under `pkg/`, a flat package or a group; `TestPackageCatalogsComplete` requires a row in README.md's package table and in `docs/en/index.md` for every flat package and every package directly under `pkg/online` (the `uncatalogedGroups` map exempts `pkg/tooling`, whose packages the site's API reference lists), requires `docs/en/index.md` and `docs/zh/index.md` to list the same import paths in the same order, and refuses a row for a package that does not exist; `TestNoStdPackageNames` is the naming rule above. Subpackages such as the pixelfx categories, the store drivers and the editor's subpackages are covered by their parent's row and by `docs/{en,zh}/stability.md`.
- Format IDs on `docs/{en,zh}/formats.md` (`<!-- format: online/accounts -->`, `pathfind/navbake`, `tooling/gamedebug`) are the package path relative to `pkg/`; `internal/formattest`, `internal/repocheck/formats_test.go` and `conformance_test.go` strip the `pkg/` prefix when matching packages to entries. `internal/apiref` is the one format whose ID is not under `pkg/`, and its ID is its path from the module root.
- A rename keeps a value that versions a format rather than naming a path: `vehicle3d` hashes its snapshots under the domain `vehicle.Vehicle.v1`, because the domain versions the hash format and renaming it would change every golden checksum in `determinism_test.go` without changing behavior. Error prefixes, format IDs and storage keys follow the package name.
- `pkg/ai` declares `type Vec3 = pathfind.Vec3`: the alias keeps the 3D steering API's `ai.Vec3` name while the stable `ai` and `pathfind` share one vector type without importing the experimental `math3d`. The stability tier forbids that import whatever the compatibility policy is.
- `pkg/editor` re-exports the profiler's public types as aliases of `internal/profiler` types (`ProfilerFrame = profiler.Frame` and so on), and godoc shows an alias's fields without the field documentation, which lives in the internal package.
- `docs/{en,zh}/stability.md` and `skills/nsgo-game/references/packages.md` list packages relative to `github.com/nsgo-dev/` (`game`, `game/cmd/<name>`, `game/pkg/<name>`), and `website` strips `pkg/` for the catalog groups and the API sidebar.
- `.github/labeler.yml` gives each flat package its own `pkg/<name>` label; a group directory takes one label for everything under it (`pkg/online` also covers the daemons and `examples/dedicatedserver`, `pkg/tooling` covers its subpackages and the shared `library/` index), and nested packages share their parent's label.
- Website unit tests use the `*.spec.ts` suffix, so `bun test` finds them while `go tool nsgo test ./...` at the module root does not take them for NSGo TSX tests.

## Alternatives considered

1. **Keep the module in `packages/game` as a Go submodule**: the repository root stays minimal and no import rewrite is needed. Rejected because every release needs `packages/game/vX.Y.Z` submodule tags and every import path repeats `packages/game`; re-examined with the rest of the layout and still rejected for the same reason.
2. **Flatten `pkg/<name>` into the module root**: gives the shortest import paths (`github.com/nsgo-dev/game/sprite`). Rejected because nearly eighty package directories would sit beside about fifteen non-Go trees (`website`, `docs`, `design`, `library`, `skills`, `template`, `tools`) and clash in meaning (`library/` against `tooling/library`); "`pkg/` is the importable library" is the simpler rule. `packages/<name>` instead of `pkg/<name>` was weighed too and loses on length and Go convention.
3. **Group core, 3D or math packages (`pkg/core/sprite`, `pkg/3d`, `physics/physics3d`)**: a deeper tree looks more organized. Rejected because these segments carry no rule a reader can apply, `3d` cannot be a package name so `pkg/3d/render3d` stutters or forces aliases, `core` reads as `nsgo/core`, and `physics3d` does not import `physics`. The 2D/3D suffix rule gives the signal without the depth. Renaming the unsuffixed packages to `physics2d`, `scene2d`, `skeletal2d` or `navbake2d`, or `anim3d` to `skeletal3d`, was weighed under the same rule and rejected: an unsuffixed name already reads as 2D or agnostic, `scene` also holds `HUD3D` and `Overlay3D`, and `anim3d` describes its package more accurately.
4. **A `pkg/genre` group**: it would separate genre kits from engine packages. Rejected because no rule decides membership and its edges are fuzzy (`fog`, `undo`, `rooms`, and `inventory`, `quest`, `loot` and `stats`). Membership by dependency (imported only by templates) admits `undo` and `vehicle3d` while leaving out `framedata`, `fog` and `rooms`, which `pkg/tooling/gamedebug`, `pkg/worldmap` and `pkg/editor` import from non-test code even though only one genre uses each. If a genre group is wanted later, membership must be by purpose, and `framedata` and `rooms` move with it.
5. **Serve every template from the root module** (`template/<name>` flattened, a `game/template` package embedding them, `nsgo init -template github.com/nsgo-dev/game#<name>`): it removes the sixteen template modules and the 365-file embedded copy under `internal/gamecli/_templates/projects`. Not adopted: template creation would break between merge and the next tag because `go.mod.tmpl` must pin a release that does not exist yet (the template pin that ends a layout change that moves template imports shows that cost each time), NSGo v0.3.4 has no default template for a `template/` directory of named templates (`init_module.go:70-74`), and every root `nsgo check` / `nsgo test ./...` would vet sixteen more `package main` programs for every target.
6. **Plural `templates/`**: reads better next to `examples/`. Rejected because NSGo v0.3.4 `init_module.go:40` hard-codes `template/`.
7. **`pkg/pixelfx` as its own module**: it would keep its 18 MB of golden PNGs out of the root module zip. Rejected on the merits and replaced by the `pkg/pixelfx/testdata` stub module, which keeps the goldens out of the zip by itself. `pixelfx` has no non-test import of another root package, but a split does not shrink downloads (`game pixelfx` in `cmd/game` keeps requiring it, and module zips are fetched whole), it has no release cadence of its own, and the root module would pin an untagged `pkg/pixelfx/vX` between merge and tag. Per-category stub modules (22 modules for one generator), Git LFS (module proxies ship the LFS pointers), a top-level `testdata/pixelfx` (still in the zip), a `pixelfx/fx` grouping (stutter), renaming the `ui`, `status`, `spawn` and `moves` categories (changes the effect-ID contract) and splitting the 28-file `core` (always imported together) were weighed and rejected for the reasons in parentheses.
8. **Separate modules for `gameschema` and `gameapi`, or `sizeprobe` under `tools/`**: smaller, independent tool modules. Rejected because one tools module is enough for repo-only commands, and `sizeprobe` must build and vet against the root module for every target, which `internal/` gives it.
9. **Other moves and renames**: `apps/website` to `website/` is adopted (`apps/` held nothing else). The rest stay rejected because none makes a path clearer and several break contracts: `docs/<lang>/<group>/*.md` instead of flat docs (the slug is the URL, the target of more than 750 links, the key of the stability guide column, of `DOC_ORDER` and of the site's `groups.ts`, and `/docs/api/` is taken), design files beside `pkg/editor` (non-Go artboards cited by path in about 150 places, and the labeler already ties `design/**` to `pkg/editor`), renaming `benchmarks/` (the default directory of both `game bench` and `game size`), moving `library/` (published data named after `game library`, with a published raw URL for `library/index.yaml`), `internal/gamecli/_templates/generate` to `_generate` (its parent's underscore already hides it), renaming `examples/tutorial/chNN-*` or `.github/workflows/notes.yml` (churn), and stub `go.mod` files for `website`, `docs`, `design` or `.agents` (about 10 MB of non-Go trees, and an empty module says nothing about the layout).
10. **Split `pkg/editor` into feature packages**: the 27 features would each get a package. Rejected because `Editor` has 446 fields and 4,323 methods, methods cannot leave the type's package, 2,902 objects cross the boundaries (1,303 of them unexported), and the MCP rule that every action is an exported `Editor` method would break. Extracting the large features (agent, view2d, view3d, tiles, review and so on) behind a `Host` is rejected for now because their host surfaces of 100 to 270 members exceed the features. Public feature packages (a double public surface), one merged `internal/live` (no shared state), `pkg/editor/history` (43 unexported `History` internals used elsewhere), moving `spec_panel_ui.go` into `theme` (46 helpers to export), a package for `local_agent_detect.go` (two functions), `internal/proc` for the platform shims (tied to feature types) and a test-only screenshots package (Go keeps tests with their package) were weighed and rejected for the reasons in parentheses.
11. **Move the editor to `pkg/tooling/editor`, rename `editormcp` to `mcp` and `editorcmd` to `cli`, fold `cmd/editor` into `game editor`**: it would put every non-release package under one group. Rejected because the editor is a product tree (the `pkg/editor` rule says so instead), `mcp` collides with `pkg/mcp`, which `editormcp` imports, `editorcmd.Main` reads clearly in generated code, and `cmd/editor` carries its own `nsgo.yaml` and signed bundle. One binary for `game` and `nsgo-game` is impossible: NSGo's extension lookup matches the module tool `game` and the `PATH` program `nsgo-game`, and `go install` names binaries after the last path element.
12. **Split `internal/gamecli` into per-command subpackages**: smaller packages per command. Rejected because every command shares unexported plumbing (`app`, `usagef`, `newFlagSet`, completion) and cross-command helpers, and its three importers each want every command. Merging `game project check` into `game check` is a behavior change, not a layout change.
13. **Other `internal/` and `pkg/tooling` moves**: an `internal/testutil` grouping, `devimage` into `pkg/assets/internal` (impossible: `pkg/tooling/hotreload` imports it too), `releaseplan` into `pkg/editor/internal` (impossible: `internal/gamecli` imports it), moving `gametest` or `loaderr` into `internal/` (games import `gametest` and `statedump` from tests, and callers need `errors.As` on `*loaderr.Error`), and moving `statedump`, `gametest` or `mcp` into `pkg/tooling` (their real code is linked by release builds and `pkg/mcp` has no release stub). Rejected for the reasons in parentheses.
14. **Other package splits and names**: splitting `render3d` into gizmo, debug draw and stats packages (they share `Queue`, `RenderStats` and `CameraBasis` with the pipeline), splitting `ai` into `ai/bt`, `ai/goap` and `ai/utility` (an API redesign of about 40 `BT*` identifiers, not a move), replacing `ai.Vec3` with `math3d.Vec3` (see the alias contract above), regrouping `pkg/online` by role, merging the `gameui` and `screen` viewports (an API merge of its own), and the names `nav`, `pool`, `arena`, `path`, `overlay`, `inspect`, `diag`, `devhud`, `devtools` and `debugkit` (common locals, standard library `arena` and `path`, too narrow or too vague, the NSGo DevTools collision; `debugkit` loses to `gamedebug`, which follows the `game` prefix rule). Rejected for the reasons in parentheses.

## Consequences

- **Benefits**: a path says what a directory is (public import path, shipped binary, repo-only tool, fixture or editor feature), and the placement and naming rules decide where new code goes and what it is called without a discussion. Releases use plain root tags. `cmd/` matches what users can `go install`, and the stability table, catalog and labels follow the same groups, with a test that fails when a new package misses one of them. No package shadows a standard library package, a game that uses one SQL driver links only that driver, and the published module zip carries no golden images.
- **Costs**: import paths, package names, commands, format IDs, error prefixes, doc slugs and example app IDs change for users, each listed in `changelog.d`: the daemons (`game/cmd/accountsd`, `cloudsaved`, `leaderboardd`), `pkg/online/*`, `netplay`, `gameserver` and `accounts/authtoken`, the cloudsave drivers in `cloudsave/sqlitestore` and `cloudsave/pgstore`, `pkg/pathfind` and `pkg/pathfind3d` (with their `navbake` and `navbake3d`), `pkg/ai/cover3d`, `pkg/dialogue`, `pkg/mempool` and `pkg/spatial`, `pkg/postfx`, `pkg/vehicle3d`, `pkg/tooling/gamedebug`, `refs`, `playtest`, `atlaspack` and `sizecheck`, `pkg/editor/theme` and `pkg/editor/keychain`, `game size` and `game project` in place of their own binaries, `pkg/tilemap/tileshape`, the promoted `ktx2`, `importsettings`, `datatable` and `jsonschema`, and `gameschema`, `gameapi`, `apiref` and `wasmprobe`, which are not public. Renames change identifiers that only the build catches, and docs mentions such as `ai.NavMesh` or `debug.X` are checked by no test, only by `git grep`. A layout change that moves what a template imports leaves the `GOWORK=off` templates CI job failing until `go.mod.tmpl` pins a commit that has the new paths. `game size` builds `cmd/game`, so the quality workflow pays for building the editor and `pixelfx` on a cold cache.
- **Kept on purpose**: sixteen template modules and the embedded copy under `internal/gamecli/_templates/projects` stay, with the duplication that implies (see alternative 5). `pkg/editor` stays one package (see alternative 10).
- **Open follow-ups**: move `remote*.go` to `pkg/editor/internal/remote` once its fields live in a `remoteState` and it reads the document through a snapshot API instead of `e.Doc`; extract a second wave of editor features (`states`, `assetgen`, `hud`, `cutscene`) once `internal/profiler` shows what the forwarders cost; add a CI job that builds with `-tags release`, since `nsgo check` cannot pass extra build tags and no job compiles the `gamedebug`, `hotreload` and `devstate` stubs; deduplicate the `gameui` and `screen` viewports; share `game.yaml` parsing between `internal/gamecli/release.go` and `pkg/project`; split `ai` into `bt`, `goap` and `utility` packages. Each is a change of its own, not a move.
- **Verification**: `go tool nsgo check`, `go tool nsgo test ./...`, `go tool nsgo test ./internal/repocheck` (catalogs, standard library names, formats, stability and conformance against the layout) and `cd tools && go tool nsgo test ./...`, the examples and templates CI jobs, `go run ./tools/changelog check`, `bun run verify-notes`, and the website's `bun run test` and `bun run build`. The release-tag stubs are verified only by `GOFLAGS=-tags=release go build` of `cmd/editor` and `internal/sizeprobe` and by a `workflow_dispatch` run of `release.yml`. `git grep` for the moved paths (`pkg/debug`, `pkg/perf`, `pkg/effects`, `pkg/vehicle`, `ai/navbake`, `online/server`, `accounts/token`, `cmd/sizecheck`, `cmd/gameproject`, `apps/website`, `vnsample`, `spec_theme`) outside `.agents/notes`, `CHANGELOG.md` and the `changelog.d` fragments that describe the moves returns nothing, and `git grep` for the old qualifiers (`ai.NavMesh`, `world3d.Nav`, `perf.`, `effects.`, `vehicle.`) in `docs`, `skills` and `pkg/editor/locales` finds only local variables and `runtime/debug`.
