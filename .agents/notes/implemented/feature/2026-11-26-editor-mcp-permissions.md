# Agent Note: Project MCP permission profiles and rules in permissions.yaml

Status: implemented

## Problem

The NSGo Game Editor serves project editing and testing tools to coding agents over MCP (`packages/game/editor/editormcp`, see [The editor's MCP server on a per-project local endpoint](../../implemented/architecture/2026-11-25-editor-mcp-server.md)). Before this change, every registered MCP tool ran immediately without checking whether the team or user allowed that action on the target files, violating `Spec.dc.html`'s principle *"Ask before the irreversible"*.

Additionally, the design artboards (`Settings.dc.html` and `Permissions.dc.html`) label permissions as *"Project · shared"* while naming `.nsgo/permissions.yaml` in one preview snippet, creating a conflict with the starter project `.gitignore` which ignores all of `.nsgo/`.

## Decision

Project-level MCP agent permissions are stored in a versioned, tracked YAML file **`permissions.yaml` beside `game.yaml`** (`editor.PermissionsFileName`), keeping `.nsgo/` and `.game/` reserved for git-ignored, machine-local editor state while teams track and review shared permission rules in Git alongside `game.yaml`, `playtest.yaml`, `game.index.yaml`, and `brief.yaml`.

- **Format (`editor.PermissionsFile`, `version: 1`)**: canonical 2-space YAML prefixed with `# yaml-language-server: $schema=https://game.nsgo.dev/schemas/permissions.v1.json` (generated by `cmd/gameschema` to `apps/website/public/schemas/permissions.v1.json`). `ParsePermissions` refuses unknown fields with line/column via `*loaderr.Error`, duplicate keys, YAML anchors/aliases/merge keys, trailing documents, and invalid profiles, actions, patterns, or decisions. `EncodePermissions` is deterministic and round-trips byte-for-byte identically.
- **Profiles as presets of rules**: `PermissionProfileCautious`, `PermissionProfileBalanced` (the default when `permissions.yaml` is absent), and `PermissionProfileAutonomous` each populate a 7-rule first-match-wins table over `(action, patterns) -> decision`, where `action` is `edit`, `create`, `delete`, `run`, or `code`, `patterns` are slash-separated file globs (supporting `**` across zero or more path segments) or run targets (`game check`, `playtests`, `shell`), and `decision` is `allow`, `ask`, or `deny`. Editing individual rules retains `profile` so `IsModified()` marks the profile as changed from its preset.
- **MCP enforcement (`editormcp.Server`)**: every non-read tool call (`Action` other than `ActionRead`) is evaluated against `ed.EvaluatePermission` *before* its handler is invoked.
  - `allow` runs immediately.
  - `ask` invokes `Options.OnPermissionAsk` (supporting `AllowOnce`, `AllowAlways`, `Deny`, and `Pending`), or queues a pending request on `Editor` and returns a structured `*editormcp.PermissionError` (`decision: "ask"`) without running the tool. Answering **Always** inserts a specific `allow` rule immediately ahead of the asking rule (so first-match-wins takes effect at once), saves `permissions.yaml`, and shows the `"Always permission rule saved"` toast with **Show** and **Undo** (restoring the exact previous bytes or removing a newly created file).
  - `deny` records a `BlockedPermissionStep` on `Editor`, returns a structured `*editormcp.PermissionError` naming the exact rule number, rule summary, profile, and Settings link (e.g. `"Settings › Permissions · rule 7 of 7"`), and never calls the tool handler.
- **MCP-only boundary**: rules govern only tools invoked through `editormcp`. External agent file edits and shell commands remain governed by the external agent's own settings and surface in the editor through the disk watcher.
- **Settings › Permissions UI (`PermissionsSettingsView`)**: renders the three profile cards (preserving the profile name with a `Changed` badge after rule edits), the reorderable rule table with an arrow-key-navigable `Allow / Ask / Deny` radio group per row, add/remove controls, and an Agent rail with blocked-step links and Ask approval cards using only `Spec.dc.html` color tokens. Clicking a blocked step link opens Settings › Permissions and moves focus to the matching rule row.

## Alternatives considered

### Store shared rules at `.nsgo/permissions.yaml` and un-ignore it in `.gitignore`

This matches the literal preview string in `Permissions.dc.html`. It was rejected because every existing starter template `.gitignore` ignores all of `.nsgo/`, so teams would either silently fail to commit their shared rules or have to maintain negation rules (`!.nsgo/permissions.yaml`) in every project template and existing repo. Putting shared rules in `permissions.yaml` beside `game.yaml` matches `playtest.yaml`, `game.index.yaml`, and `brief.yaml` with zero `.gitignore` churn.

### Append "Always" rules to the end of the rule table

Appending a new `allow` rule to the bottom is simpler to implement, but under first-match-wins an earlier `ask` rule (such as `run: [game check, playtests] -> ask` in `Cautious`) would still match first and keep asking. Inserting the new `allow` rule at the matched rule's index guarantees the newly allowed action passes on the next call while leaving sibling patterns (such as `game check`) untouched.

### Store permission state inside `EditorSettings` (`editor.yaml`)

Keeping permissions in per-user `editor.yaml` avoids adding a new project file format. It was rejected because permissions are a shared project policy that teammates review in Git, whereas `editor.yaml` holds per-computer preferences (language, appearance, viewport overlays) outside any repository.

## Consequences

- **Benefits**: every mutating or running MCP tool call has a deterministic, explainable permission verdict traceable to an exact rule or profile; `deny` rules strictly prevent handler execution; teams review permission changes in plain text Git diffs with JSON Schema validation; users can inspect blocked steps, jump straight to the matching rule, and undo any accidental "Always" approval byte-for-byte.
- **Costs**: existing `editormcp` unit tests that invoke non-Balanced tools (such as `tileset_edit`, `states_write`, `cutscene_write`, `playtest_define`, `merge_abort`, or custom `ActionRun` tools) without a `permissions.yaml` must explicitly select a profile or supply `OnPermissionAsk`, reflecting the real security boundary. `packages/game/editor` gains a second project-level YAML format alongside `editor.yaml` and recent projects, tracked in `cmd/gameschema` and `formats_test.go`.
