# Agent Note: Editor inspector adds and removes components and properties, and edits sprite, origin, flip and material

Status: implemented

## Problem

The editor's inspector (`packages/game/editor`) could change the values of an object's existing components and properties, but setting an object up still needed hand-edited YAML: a component or a property could not be added or removed, and the sprite, origin, flips and material had no controls. Issue #865 asks for all of these as undoable inspector edits that save and reload byte for byte. Three constraints that the code does not state make this more than wiring controls:

1. A component declares events and handlers that the scene's connections name, either bare (`pressed`) or qualified (`button.pressed`). Adding or removing a component can make a connection ambiguous or leave it pointing at nothing, and a scene whose connections do not bind fails to open with a registry (`sceneformat.ParseWith`) and to play.
2. Custom properties have no schema. The YAML encoder writes `float64(2)` as `2`, which reads back as an int, so a float property added at its zero value (`0.0`) or edited to a whole number changed kind after one save and reload, and the inspector then built an int control for it.
3. The issue wants a duplicate component refused in the status bar, while also listing only the types an object lacks.

## Decision

- Every edit is a method on `Editor` that goes through `History` and returns `ErrPlaying` during Play: `AddComponent`, `RemoveComponent`, `ComponentConnections`, `AddProperty`, `SetObjectSprite`, `SetObjectOrigin`, `SetObjectFlip` and `SetObjectMaterial` (`objectedit.go`). The inspector (`inspector.go`, `inspector_edit.go`) only calls these and sends a refusal to the status bar through `ed.report`, so a script, a test and the UI share one set of rules.
- `AddComponent` adds a registered type holding every registered field at its default, so the saved file shows what the component does; without a registry it adds an empty component. Before adding, it puts the component in place temporarily and runs `sceneformat.ValidateConnections`, refusing the add when a bare event or handler would become ambiguous. A scene that instances or inherits others binds its connections only once resolved, so it is resolved through the editor's resolver (`sceneformat.Resolve`) first, and the check is skipped when the resolver is not a `SceneResolver` or the scene already fails to resolve or bind without the new component, since adding a component neither causes nor fixes that fault.
- `RemoveComponent` removes the component together with every connection that needs it (from the object with an event the component declares, or to the object with a handler it declares) as one step, and Undo restores the connections at their original indexes. A bare name is attributed through the component's registered type, so without a registry only qualified connections are removed; the docs state this.
- `sceneformat.Encode` encodes a copy of the document in which every whole-number float inside custom properties (`ObjectDoc.Properties` and `ObjectOverride.Properties`, at any depth) is a `wholeFloat` that writes a `!!float` scalar such as `2.0` (`propfloat.go`). The document passed in is not changed, ints stay ints, and a document that holds no whole-number float property encodes exactly as before.
- The Add Component control is a filter field plus one button per registered type the object lacks, and Enter adds whatever name the field holds (or the single match). Typing an existing name therefore reaches `AddComponent`'s refusal, which is what the status-bar requirement tests.

## Alternatives considered

- **Refuse `RemoveComponent` while connections need the component**: keeps the scene's connections untouched and makes the user delete them first. Rejected because the editor has no connection list to delete them from, so a component with a connection could not be removed at all; removing them in the same undoable step, with `ComponentConnections` listing them beforehand, keeps the scene binding and loses nothing on Undo.
- **A schema or registry for custom properties to restore float kinds on load**: would fix the kind at parse time and also cover unregistered components. Rejected as out of scope: it is a new on-disk contract, and properties are deliberately free-form. Marking floats on the encode side fixes the round trip with no format change for files that already parse.
- **Also mark whole-number floats in component fields**: would cover components without a registered type, which still save `2` and read back an int. Rejected for now because registered float fields already decode back to floats, and writing them as `2.0` would change the bytes every existing scene re-saves with (`mass: 1` becoming `mass: 1.0`), breaking the no-op round trip for files already on disk. The gap for unregistered components is documented in `docs/en/editor.md` and `docs/zh/editor.md`.
- **Skip the ambiguity check for scenes that instance or inherit others**, as `SetComponentRegistry` skips its connection check: simpler, but such a scene would accept an ambiguous component, save, and then fail to bind at Play. Resolving first costs one `Resolve` call per add and catches it.
- **Drag and drop a frame from the asset browser onto the inspector for the sprite**: closer to other engines. Not done because a searchable `ui.Select` over the asset browser's frames plus a "use selected asset" button covers the acceptance criteria without a cross-panel drag contract.

## Consequences

- **Benefits**: an object can be set up entirely in the inspector, every step is undoable and saves to the same bytes after a reload, and the scene's connections keep binding after any add or remove.
- **Costs**: `AddComponent` in an instancing or inheriting scene resolves the whole scene twice, which loads every scene file it refers to. Bare-named connections are not removed with a component when no registry is set. Unregistered components' whole-number float fields still read back as ints.
- **Verification**: `packages/game/editor/objectedit_test.go` drives both acceptance scenarios through the inspector with nsgotest (add physics, uncheck a field, flip X, remove the component, each saved and reloaded byte-identical, then undone; duplicate component, unregistered name and empty or duplicate property key refused in the status bar with no history step), plus connection removal and its undo, the ambiguity refusal in a plain and an instancing scene, every setter's validation, and `ErrPlaying`. `packages/game/sceneformat/sceneformat_test.go` checks whole-number float properties on objects, children, scene overrides, instance overrides and nested `map[any]any` values.
