# Agent Note: Room-template dungeon generation on a lock/key layout graph

Status: implemented

## Problem

`game/procgen` generates levels with BSP partitions, cellular-automata caves, and wave function collapse, which construct whole maps from noise or tile adjacency rules rather than hand-authored rooms. Action roguelikes and roguelites need a way to author reusable room templates in plain-text YAML (inline tile grids or `.tmj`/scene references with door sockets, tags and weights), generate a dungeon layout graph with a critical path, side branches, cycles, and lock/key pairs where every key is guaranteed reachable before its lock, and place those templates deterministically without overlap while maintaining `Grid.Connected`.

## Decision

Extend `packages/game/procgen` with three cohesive components (`room_templates.go`, `dungeon_graph.go`, `dungeon_rooms.go`):

- **Versioned YAML room templates (`RoomTemplatesVersion = 1`, `ParseRoomTemplates`, `EncodeRoomTemplates`)**: Each `RoomTemplate` carries a unique `id`, optional `weight` (default 1), optional `tags`, optional `allowRotate`, non-overlapping `doors` (`side`, `offset`, optional `width` defaulting to 1, optional `channel`), and mutually exclusive inline ASCII `tiles` (`#`, `.`, `a`..`z`) or an external `source` path (`.tmj`/scene) with explicit `width` and `height`. Decoding refuses unknown fields (`KnownFields(true)`), unsupported versions, trailing documents, and disconnected inline rooms. Encoding writes deterministic 2-space YAML checked by `formattest.Run` under `procgen#rooms`. `GridFromTilemap` bridges `tilemap.LoadTiled` into `ResolveGrid`, and `Source`-only templates without a resolver stamp a walled walkable footprint so `Grid` remains connected.
- **Tier-partitioned layout graph (`GenerateGraph`, `LayoutGraph.VerifyLocks`)**: Locks placed along the critical path partition nodes into monotonic progression tiers `0..Locks`. Every branch room inherits its parent's tier; every lock `k`'s key is placed in a non-Start, non-Goal room of tier `k` (preferring an existing branch leaf or growing a dedicated key room in tier `k`). Loop edges are restricted to pairs within the same tier so loops never bypass a lock, and in `GenerateGraph` further restricted to opposite spanning-tree parity so cycles have even length (4, 6, ...) and remain embeddable on orthogonal 2D grids. `MaxDegree` defaults to 4 to match cardinal room sides.
- **Dual deterministic placement (`GenerateRooms`, `PlaceRooms`)**:
  - `PlacementStitch` (default) stitches variable-sized (and optionally 90°-rotated) room templates by matching door sockets without rectangle overlap using bounded backtracking weighted by template weights. When `Loops > 0`, candidates that align unused doors with same-tier placed rooms are preferred and aligned same-tier door pairs are wired into loop edges.
  - `PlacementGrid` (Spelunky-style) embeds uniform-sized templates on a coarse `GridCols × GridRows` slot grid (starting on row 0 with horizontal/downward path bias), grows branches and key rooms into free adjacent slots, wires same-tier adjacent loops, and assigns templates whose sockets match across every shared edge.
  - Both modes normalize coordinates onto a single `Grid`, seal unused door sockets with `Wall` (without clobbering shared open cells), open connected door cells, and verify `Grid.Connected`, retrying deterministically from the caller's `random.Stream` up to `Attempts` before returning `ErrNoLayout`.

## Alternatives considered

- **Placing keys anywhere in the graph and rejecting invalid seeds by post-check** — Simpler to write, but rejection rates explode as `Locks` grows (especially with 3+ sequential locks and loops), wasting stream draws and causing sporadic `ErrNoLayout` failures. Partitioning nodes into lock tiers by construction guarantees 100% key reachability and zero lock bypasses on every attempt.
- **Allowing arbitrary triangle (3-cycle) loops in `GenerateGraph`** — Works for abstract graphs, but a 3-cycle cannot be embedded on a 4-neighbor orthogonal grid of uniform rooms, causing `PlaceRooms(..., PlacementGrid)` to fail on graphs generated by `GenerateGraph`. Restricting standalone graph loops to opposite spanning-tree parity ensures even-length cycles embeddable on 2D grids.
- **Creating a separate `packages/game/dungeon` package instead of extending `packages/game/procgen`** — Would split procedural level generation across two packages and duplicate `Grid`, `Rect`, `Point`, `Connected`, and `ErrInvalidConfig`. Issue #856 targets `procgen` directly so callers reuse `Grid.Paint`, `Grid.Connected`, and `random.Stream` conventions unchanged.
- **Storing door sockets as raw world coordinates or bitmasks** — Bitmasks cannot express multiple doors per side, non-centered offsets, wide openings, or channel compatibility. Explicit `DoorSocket{Side, Offset, Width, Channel}` entries stay readable in YAML and support both uniform grids and asymmetric rooms.

## Consequences

- **Benefits**:
  - Same `random.Stream` seed produces bit-identical `Grid`, `Rooms`, `Doors`, and `Graph` across platforms; no map iteration affects layout or YAML output.
  - Lock/key solvability and non-bypassability hold structurally over 1,000+ tested seeds in both `PlacementStitch` and `PlacementGrid`, verified both on `LayoutGraph` and directly on the stamped `Grid` with locked doorways walled off.
  - Author-created `.tmj`/scene rooms work immediately via `source` + `ResolveGrid` (or default footprints) while keeping every template file plain-text YAML.
- **Costs and known limits**:
  - `PlacementGrid` requires all templates in the active `RoomTemplates` set to share one uniform dimension (after rotation). Mixed-size template sets must use `PlacementStitch`.
  - In `PlacementStitch` with arbitrary prime room dimensions, pre-planned loop edges may have few exact socket alignments; `GenerateRooms` therefore closes loops at geometrically aligned same-tier contacts and falls back to the highest-loop valid layout across `Attempts` if the template set cannot achieve the full `Loops` target.
