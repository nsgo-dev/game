# Agent Note: Playtest baseline declarations

Status: implemented

## Problem

Playtest configurations had metrics but no shared contract for skilled reference wins, degraded routes, or no-input outcomes, so every template wrote its own idle-loss and weak-play tests and none of those outcomes reached `playtest.report.yaml` (#1958).

## Decision

Version 1 `playtest.yaml` accepts an optional `baselines` section with `idle` (`outcome` of `lose` or `stall`, and `within`), `reference` (`winRate`) and `degraded` (`reactionScale`, `dropRate`, `maxWinRate`, `margin`). `Config.Validate` refuses an `idle.within` that is not positive or exceeds the effective `runs.maxDuration` (60s when unset), rates outside 0 to 1, a degraded policy that weakens nothing, and one without a win-rate limit; the strict decoder still refuses unknown fields. `cloneConfig` deep-copies the section, since `EncodeConfig` encodes a clone and would otherwise drop it. Reports accept a `baselines` list with one entry per policy name, and `WinRate` is a pointer so a measured win rate of 0 is written rather than omitted. The JSON Schema is regenerated by `tools/gameschema`.

## Alternatives considered

Introducing a new schema version would force every existing playtest file to migrate for an optional section, so the additive fields remain in version 1. Keeping policy only in hand-written template tests would avoid format changes but would preserve inconsistent reporting and gates.

## Consequences

Existing playtests remain valid. Only the declaration and the report data model exist: the `idle` bot profile (#1957), the degrading bot wrapper, running the three policies over the same seeds, filling `Report.Baselines`, a non-zero exit from `go tool game playtest`, the editor report view and the template declarations are still to do under #1958.
