# Agent Note: On-screen touch controls built from a YAML layout, with plugin control kinds

Status: implemented

## Problem

Games built on `game/input` were hard to play on a phone. `VirtualStick`, `VirtualButton` and `VirtualPad` existed, but nothing placed them: every template and example laid out its own controls in its own way, none read the safe area or the screen's pointer, and the controls showed on desktops too. Cave Run had two touch paths that disagreed: three native `<`, `>` and `JUMP` pills (`examples/caverun/hud.go`) merged by hand into the explorer's input, and invisible `touchRegion` rectangles in `game.yaml`. There was no d-pad, a finger could not slide from one button to its neighbour, buttons only held, and a touch stick read `AxisY` positive downward while a game controller's inverted stick reads it positive upward. A community that wants to add its own control, such as a steering wheel or a radial menu, had no extension point.

## Decision

- `pkg/input/touchlayout.go` defines `TouchLayout`, a YAML document with `version: 1`, unknown fields refused (`KnownFields`), deterministic output (struct field order, `options` sorted by yaml.v3), and a lossless parse and encode, as every YAML format here is (AGENTS.md). `EncodeTouchLayout` writes a `yaml-language-server` comment pointing at `https://game.nsgo.dev/schemas/touchlayout.v1.json`, which `tools/gameschema` generates; `pkg/input/conformance_test.go` runs `formattest.Run` against `testdata/*.touch.yaml` and the `input#touch` entry of `docs/*/formats.md`.
- A control is placed by anchor (nine points of the safe area), offset and size in points of a `reference` screen. `TouchControls.place` scales by `min(safeWidth/refWidth, safeHeight/refHeight)`, capped by `maxScale`, clamps each side to at least `MinTouchTarget` (44 points), and pulls the frame back inside the safe area. `Mirrored` swaps left and right anchors and negates a centered anchor's x offset; directions keep their meaning.
- `TouchControls` owns a `VirtualPad` with `SlideBetweenButtons` on, an identity `MapPoint` (controls live in view points, not the `Actions.MapPoint` canvas), and binds it to the game's `Actions`, so `Actions.OnTouch` routes touches and the game reads the same action and axis names for every device. It never routes touches itself, so no touch is handled twice.
- Visibility: initial state is `Env.Pointer() == core.PointerCoarse`. An internal `DeviceTracker` shows the layer on a touch and hides it on a key or a controller. `TouchControls.Attach` wires only the tracker's touch and key handlers, not `DeviceTracker.Attach`: a press synthesized from a touch reports `PressEvent.Keyboard` when a key was the last input, which would hide the controls under the finger. `Update` also hides on the rising edge of keys `WatchKeys` reads and controllers `WatchGamepads` reads, so a held key does not re-hide the layer after every touch. A press on a control and `SetVisible(true)` move the tracker to `DeviceTouch`, and `SetVisible(false)` moves it off `DeviceTouch`, because `DeviceTracker.SetDevice` only notifies on a change: without this a game that binds `Actions` but does not call `Attach` would see the controls hide on the first key and never again after a touch.
- Extension point: `RegisterTouchControlKind(name, factory)` maps a layout's `kind` to a `TouchControlFactory` returning a `TouchControl` (`VirtualControl` plus `Place(frame, scale)`). `VirtualControl` is the interface `VirtualPad.Controls` routes fingers to: `Claim`, `Move`, `Release`, `Reset`, `ActionNames`, `ActionPressed`, `AxisValues`, `Draw`. Built-in kinds `button`, `dpad` and `stick` register through the same registry. `ParseTouchLayout` accepts any kind and refuses fields the built-in kinds do not take; `NewTouchControls` refuses an unregistered kind and relocates a factory's `*loaderr.Error` under `controls[i]`. `RegisterTouchIcon` does the same for button icons. Two optional interfaces close the gap between built-in and plugin kinds: `ButtonControl` (`Button() *VirtualButton`) makes `VirtualPad` drive a plugin's button exactly as a built-in one (claim priority, sliding, tap end in `endStep`, release on cancel), and `AccessibleControl` lets a control report its canvas node's role and selected state. Both are checked by type assertion, so plugins that need neither implement only `TouchControl`.
- `VirtualPad` gains `Controls`, `AddControl`, `SlideBetweenButtons` (default off, so existing pads keep their behavior) and `OnPress`. `Actions` iterates pad actions and axes through `eachAction` and `eachAxis`, so a control's actions and axes reach `Step`, `syncRaw`, `ActionNames` and `AxisNames` like a button's or stick's.
- `VirtualButton.Mode` adds `ButtonToggle` (flips on touch-down) and `ButtonTap` (pressed until the next `Actions.Step`, cleared by `VirtualPad.endStep`). A cancel of every touch lifts fingers but keeps toggles; `Reset` clears them.
- `VirtualStick.UpPositive` is an explicit opt-in; the default stays screen-down positive because `template/fps3d`, `action3d`, `racing3d` and `fighting2d` read `AxisY` that way. The `stick` kind sets it.
- `TouchControls.Draw` names each control as a `core.CanvasNode` with its `label` and the test ID `touch-<id>`, which is how screen readers and `nsgotest` see canvas-drawn controls. The nodes are emitted at any opacity, so an `idleAlpha` of 0 (the default) hides the controls visually without removing them from assistive technology while they still take touches.
- Option values are strings (`map[string]string`, schema `type: string`). `ParseTouchLayout` walks the `yaml.Node` tree and refuses an `options` value whose resolved tag is not `!!str`, since yaml.v3 would otherwise decode `speed: 3` into `"3"` and the first save would rewrite it as `speed: "3"`. `EncodeTouchLayout` is deterministic, and a canonical document round-trips byte for byte; other valid documents (`4000ms`, block-style `reference`, extra comments) are normalized.
- The idle timer runs whether or not the game draws the layer, so `TouchControls.Wake` resets it; Cave Run calls it from `clearHeldInputs`, which every start, restart, pause and resume goes through, so the controls never first appear already faded after a long stay on the title or pause menu.
- Cave Run declares its layout in `examples/caverun/controls.touch.yaml` (an 8-way d-pad driving `left` and `right`, and a `jump` button) and drops the native pills, the hand-merged pad state, and both the `touchRegion` and `mouseRegion` bindings. The mouse regions were kept at first, but they no longer matched the drawn controls (at 960x540 clicking the d-pad's right arrow landed in the `left` region), so they were a second, invisible pointer path; a desktop player uses the keyboard or a controller. The d-pad is 104 reference points with a small offset (`{x: 4, y: 8}`), so on a landscape phone (844x390 with notch insets and fractional full-height scaling, see [landscape phone playfield scaling](../bug-fix/2026-11-27-caverun-landscape-phone-scale.md)) it leaves the explorer's spawn uncovered.

## Alternatives considered

- **Add a touch section to `game.yaml` (`pkg/project`)** — one file for the whole project, and the editor already edits it. Rejected: the layout is also a player save (`TouchControls.Save`), which must not carry the project's other fields, and a separate versioned file keeps the project schema from growing a runtime concern.
- **Flip `VirtualStick.AxisY` to up-positive** — matches the gamepad convention with no new field. Rejected: four templates read the current sign, and a silent flip would invert their movement or camera without a compile error.
- **Let `TouchControls` route touches itself through its own `Attach`** — no dependency on `Actions.OnTouch`. Rejected: games already attach `Actions`, which routes to every bound pad, so both paths would see each touch; the layer hooks only the device tracker.
- **Builder or options API for layouts in Go** — typed and discoverable. Rejected: the layout must be a text file a person or an AI edits and diffs, and the plugin surface stays one function plus one interface.
- **Route mouse presses on the drawn controls to the pad as a pseudo-finger** — would keep a pointer path that matches what is drawn. Rejected for now: the controls stay hidden on a desktop until a touch, so a mouse user would never see what they click; the keyboard and controllers already cover desktop play.
- **Refuse `idleAfter` with `idleAlpha: 0`** — would stop a layout from fading out of sight by accident. Rejected: fully hiding idle controls is a legitimate choice for games that want an unobstructed screen; the docs state it and the accessibility nodes stay.
- **Unknown kinds refused at parse time** — earlier errors. Rejected: a layout often parses before the plugin package that registers its kind is imported; `NewTouchControls` checks it, and the schema documents `kind` as an open string.

## Consequences

- **Benefits**: one touch path per game, with the same action names as the keyboard and controllers; controls respect safe areas and stay at least 44 points; a plugin adds a control kind with one `init` registration and a layout names it; the format is schema-checked and round-trips byte for byte.
- **Costs and known limits**: `ButtonTap` ends only at `Actions.Step`, so a standalone pad not bound to `Actions` keeps a tap pressed until `Reset`. The registry is process-global, so two plugins cannot register the same kind name. `nsgotest.App.Touch` gives every finger ID 1 and does not report pointer input modality, so Cave Run's two-finger tests send touches with `App.Report`. Revisit if NSGo adds a native accessibility action for canvas nodes, which would let screen-reader users activate a control, or if the layout grows per-device variants.

## Verification

- `go tool nsgo test ./pkg/input/...` runs `touchcontrols_test.go` (d-pad quantization, sliding between buttons, toggle and tap, the same through `TouchControls` buttons and a plugin `ButtonControl`, cancel and hide releasing a held d-pad and stick, hiding on every key after a touch without `Attach`, layout round trip and refusals including unquoted options, safe-area and mirrored placement, show and hide, fade to 0 and `Wake`, haptics, save and load, a plugin kind) and the format conformance test.
- `go tool nsgo test ./...` in `examples/caverun` plays the level with two fingers on the touch controls and checks that they stay hidden on a desktop until touched and inside a phone's safe area, that the d-pad leaves the explorer at spawn uncovered on a landscape phone, and that `controls.touch.yaml` is canonical.
- `go run ./tools/gameschema -check` confirms `touchlayout.v1.json` matches the Go types.
