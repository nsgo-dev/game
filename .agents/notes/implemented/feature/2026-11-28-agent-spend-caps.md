# Agent Note: Agent spend counters and caps in editor.yaml

Status: implemented

## Problem

Issue #1746: agent usage in `editor.yaml` counted requests, reviewed changes and playtest runs, but not tokens or money, so a long built-in run (up to 24 model calls) or an automation could spend a week's budget with no visible cost signal and no cap the person could set. This change is the storage and query layer of that issue; the runners, automations and the Usage page are follow-up work.

## Decision

- `AgentUsageStats` (`pkg/editor/agent_settings.go`) gains `inputTokens`, `cachedInputTokens`, `outputTokens` and `estimatedCostUSD`. They belong to `weekStart`'s week like `weeklyRequests`: `AgentUsageStats.resetWeek` zeroes all five weekly counters together, and every path that crosses the week (`AgentUsage`, `RecordAgentRequest`, `RecordAgentSpend`) calls it, so a request in a new week never inherits last week's spend and a spend record never inherits last week's request count. `reviewedChanges`, `keptChanges` and `playtestRuns` stay all-time counts.
- `AgentSettings` gains three person-only caps, `weeklySpendLimitUSD`, `requestSpendLimitUSD` and `toolCallLimit`, as pointers like `weeklyRequestLimit`, so an omitted cap stays omitted on save. `0` means no cap. The loader refuses negative caps and counters, and NaN or infinite dollar amounts (`validUSD`), naming the field in the `loaderr` path.
- `cloneAgentSettings` keeps an `agent` block whose only content is a cap or a spend counter; without that, `ApplySettings` and encoding would silently drop a cap set on its own.
- `RecordAgentSpend(input, cached, output, costUSD)` adds to this week's counters, ignoring negative counts and negative, NaN or infinite costs, persists `editor.yaml` and notifies. `AgentSpendCapReached` reports whether this week's estimated spend has reached `weeklySpendLimitUSD`, through `AgentUsage` so a stale week reads as zero.
- `website/public/schemas/editor-settings.v1.json` is regenerated by `go run ./tools/gameschema`, so the new fields are described for editors and AI tools.

## Alternatives considered

- Plain `float64` and `int` caps with the zero value meaning "unset" (the parallel PR #2009). It reads simpler, but differs from `weeklyRequestLimit`, whose pointer distinguishes "omitted, use the default" from "0, no limit"; keeping the same shape leaves room for a default spend cap without another format change.
- Using the request count as a spend proxy. Rejected because one request can cost a hundred times another depending on tool rounds and context size.
- Storing provider billing responses or per-model price tables in `editor.yaml`. Rejected for this change: costs are estimates computed by the caller, and the price table depends on the model choice in #1747.

## Consequences

- Nothing records spend or enforces the caps yet: the built-in runner, the Claude Code and Codex parsers (`total_cost_usd`, `usage`), automations and the Usage page still need to call `RecordAgentSpend`, check `AgentSpendCapReached`, `requestSpendLimitUSD` and `toolCallLimit`, and show the totals. Prompt caching and per-thread or per-automation totals are also open in #1746.
- Older editors that refuse unknown fields fail to load an `editor.yaml` that carries the new fields; the file is per-computer, so this only affects downgrading the editor on the same machine.
- `pkg/editor/agent_spend_test.go` covers the YAML round trip, a cap alone surviving encode, refused invalid values, the weekly cap and the weekly reset of every counter.
