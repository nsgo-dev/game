# Agent Note: A plain WebSocket client (wsclient) for third-party servers

Status: implemented

## Problem

The only WebSocket client in the repository was `netplay.DialWebSocket`, which speaks netplay's own protocol: a hello with a token, a welcome assigning a `PeerID`, and a 5-byte channel+seq header on every message. It cannot talk to any server that is not a `WebSocketServer` — Nakama, Colyseus, a Node/Elixir game server, Twitch or YouTube chat, a hosted realtime database, or a custom JSON protocol shared with a web dashboard (#1448, part of #1354). The RFC 6455 framing itself (frame reader/writer, accept key, HTTP upgrade) was private to `pkg/online/netplay/ws_native.go`, so a second client would have to copy it, and on the browser side a game would have to wrap `syscall/js` WebSocket itself and bridge both to the engine goroutine.

## Decision

- New package `pkg/online/wsclient`: one `Client` per target (`ws_native.go`, `ws_js.go`) behind one API, mirroring how netplay splits its `WebSocketTransport`. `Dial(ctx, url, Options)` blocks until the connection is open on every target and returns a ready client; `Send`, `SendText`, `Recv`, `State`, `Err`, `Protocol`, `Buffered`, `Dropped`, `CloseStatus`, `Close(code, reason)`. `State` is only `Open` or `Closed`: a plain client does not reconnect, so there is no `ConnConnecting`/`ConnDisconnected` to expose after `Dial` returns.
- The RFC 6455 layer moved from netplay to `pkg/online/internal/wsproto`: frame reading/writing with the slow-loris-safe payload allocation and the §5.5 control-frame checks, the accept key, `HostPort`, and a generalized `ClientUpgrade` that adds subprotocol negotiation and extra handshake headers to what netplay's dial did. netplay's `ErrInvalidPacket` and `ErrPayloadTooLarge` are now aliases of wsproto's, so `errors.Is` compatibility is unchanged, and `ws_native.go` keeps short aliases (`wsOpBinary`, `readWSFrame`, …) so the netplay call sites and the frame-level internal tests are untouched. netplay's transport keeps its own session logic (hello/welcome, resume, keepalive) and only shares the wire format.
- `Options.Header` is native only and fails a browser `Dial` with `ErrHeadersUnsupported` rather than being silently dropped; `Options.Protocols` works on both targets, and a server that answers a subprotocol the client did not offer fails the dial. `Options.MaxMessage` (default 4 MiB, netplay's cap) bounds both directions: a larger incoming message closes the connection with 1009 and `Err` reports `ErrMessageTooLarge`. `Options.MaxInbox` (default 256, negative for unbounded) bounds the `Recv` queue; past it the oldest message is dropped and `Dropped` counts, because WebSocket is a reliable ordered stream and the only safe thing to lose is the stalest state.
- The native client answers pings with pongs but sends no pings of its own and sets no idle timeout, because a third-party server may stay silent arbitrarily long; netplay's 2s ping / 10s idle keepalive is a netplay contract with its own server, not something to impose on others. Protocol violations a lenient reader could paper over (a new data frame mid-fragment, a stray continuation) close the connection with 1002 and `ErrProtocol`, so interop bugs surface at the boundary.
- `CloseStatus` follows RFC 6455 conventions: the peer's code and reason when it closed first, otherwise the ones `Close` was called with, `CloseNoStatus` (1005) when the close frame carried no code, and `CloseAbnormal` (1006) when the connection dropped with no close frame at all. `Close` validates the code against the ranges §7.4 allows an endpoint to send, because the browser throws on the reserved codes.
- The browser client blocks `Dial` by parking its goroutine on a channel until the socket's `onopen`/`onerror`/`onclose` fires; Go's wasm runtime returns to the JS event loop while every goroutine is parked, so the callbacks still run. This keeps one blocking `Dial` contract across targets instead of netplay's async browser `DialWebSocket` with its queued pre-welcome sends, which only exists because the netplay handshake must ride the first message.

## Alternatives considered

- **Rebuild netplay's `WebSocketTransport` on top of wsclient**, as the issue sketches, so both share one client per target. Deferred: netplay's transport carries session semantics a plain client must not have (hello/welcome with token and resume secret, `Reconnect` with a special close code, admissions counting, a 2s/10s keepalive, pre-welcome send queueing on the browser), and pushing all of that into wsclient's options would double its API for every user to serve one internal caller. The shared layer is the wire format and the opening handshake in wsproto; netplay's tests (455 in `pkg/online`) pass unchanged against it. Revisit if a third WebSocket-speaking package appears.
- **A third-party WebSocket module on native** (`coder/websocket`, `gorilla/websocket`) — battle-tested, and browsers would still use `syscall/js`. Rejected: the repository already owns a hardened RFC 6455 implementation (slow-loris allocation, control-frame checks, deadlines around `Close`), the project rules prefer no new dependencies where the capability exists in-repo, and one implementation per target keeps behavior identical between netplay and wsclient.
- **Unbounded inbox like Godot's `WebSocketPeer`** — simpler, nothing ever dropped. Rejected: a game that stops draining (a paused menu over a chatty socket) would grow memory without bound; every transport in this repository bounds its inbox, and the count cap matches netplay's model with drop-oldest for the reliable stream.
- **Async browser `Dial` returning in a `Connecting` state**, like netplay's browser transport — avoids parking the caller. Rejected: it leaks a state machine into every caller (queue-or-fail on `Send`, poll `State`) for a convenience only the browser needs, and a blocking dial during loading is the natural shape for third-party backends; documented that a web `Dial` suspends its goroutine and must not run inside a frame callback.

## Consequences

- **Benefits**: games talk to any `ws://`/`wss://` server with one API on native and web; netplay and wsclient share one RFC 6455 implementation, so framing fixes (like the #546 slow-loris work) apply to both; netplay's public behavior is unchanged — its errors keep their identity and its tests run untouched.
- **Costs and known limits**: no `permessage-deflate` or other extensions (left to #1447); no client-initiated ping, so a dead network is noticed only at TCP's own pace; the browser path is compile-checked (`go tool nsgo check -target web`) but has no end-to-end test, because the repository has no headless-browser harness; `MaxInbox` counts messages, not bytes, so a worst-case backlog is `MaxInbox × MaxMessage`.

## Verification

- `go tool nsgo test ./pkg/online/` — 455 passed, including all netplay WebSocket tests after the refactor and the new `ws_test.go` suite: text and binary echoes against an in-process server, server pings answered, fragmented messages reassembled (frames written by hand, not through wsproto, to stay honest), close codes and reasons in both directions, subprotocol negotiation and mismatch, handshake headers, refused upgrades, oversized messages refused with 1009, send-side size cap, the bounded inbox dropping oldest, canceled dial contexts, invalid close codes, and abnormal drops reported as 1006.
- `go tool nsgo check -target web ./pkg/online/wsclient/` — the `syscall/js` client compiles for the browser.
