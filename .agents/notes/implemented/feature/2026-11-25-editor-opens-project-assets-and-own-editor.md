# Agent Note: The editor opens a project with its own atlases, scene files and component types

Status: implemented

## Problem

`go tool game editor <dir>` opened a project's game.yaml and main scene but kept the demo room's resolver (two in-memory atlases) and its component registry (only `body`). A real project's sprites did not draw, its atlases were missing from the asset browser, a scene with any other component failed to open, and placing a scene instance failed because the resolver could not load scene files. Only a game that wrote its own editor command, as Field Medic does, got a working editor (#905).

## Decision

- **One asset rule for `game check` and the editor**: `project.Resolver` (`packages/game/project/resolver.go`) loads atlases, scene files (`sceneformat.FSScenes`), materials (`resource.Library`) and, through `ReadFile`, YAML tilesets and Tiled and LDtk maps from an `fs.FS` rooted at the project, and implements `sceneformat.AssetResolver`, `SceneResolver`, `MaterialResolver`, `PhysicsMaterialResolver` (so the editor's Play finds `.physics.yaml` files), `FileResolver` and `editor.AtlasLister`. The name rule lives in `project.NearestAtlases` and `project.AtlasNamed`, which `tooling/assetcheck`'s `findAtlas` and `atlasNotFound` now call, so a name `game check` accepts is the name the editor draws; `AtlasNamed` cleans the name as a path from the root, as assetcheck's old `path.Join(root, name)` did, so `game check` keeps accepting what it accepted. The walk skips what assetcheck skips (`project.SkipDir`: `.`/`_` directories, `testdata`) and nested projects (a directory with game.yaml, nsgo.yaml or go.mod), and both tell atlases from other JSON with `project.IsAtlasJSON`. `ForScene` gives a view sharing the caches that measures "nearest" from one scene. `sceneformat.Build` resolves instanced and inherited scenes first and then looks every atlas name up through the one resolver, so `Resolver.Scene` rewrites each atlas name in a loaded scene file (sprites, overrides' sprites, inline tilemaps' tilesets) to the root-relative stem of the one atlas that name finds nearest that file, the binding `game check` makes per file; a name that finds none or several is left for `Atlas` to report. The open scene itself is not loaded through `Scene` (`editedScene` serves it), so the names it saves are the author's. Atlas listings, parsed atlases and the `resource.Library` of materials are cached until `Refresh`, which replaces the library too, since `Rebuild` runs after every edit; scene files are read per request so a scene the editor just saved is seen by the scenes that instance it. The image path rule (`ResolveRef`, `HasScheme`) moved from assetcheck into package project with the name rules, so `meta.image` is accepted on the same terms by both.
- **Tilesets and maps go through `sceneformat.FileResolver`**: `sceneformat.Build` reads layered tilemaps' YAML tilesets and Tiled and LDtk sources itself through a `FileResolver` (`ReadFile`), as `sceneformat.FSAssets` serves them for `go tool game editor`, and the tile palette reads tilesets the same way. `Resolver` implements `ReadFile` and deliberately not `TilemapResolver`, which `Build` would prefer for a source without a level: an earlier version of this change converted a Tiled map into a one-tileset inline grid there, which `Build`'s own loader, with several tilesets, flips and LDtk, supersedes. Like `FSAssets`, `Resolver` implements no `ImageResolver`, so tile images stay URIs and a missing tile image is not a build error.
- **The editor opts in**: `Editor.ProjectAssets` makes `OpenProject` and the new `OpenProjectScene` install a `project.Resolver` before the scene opens (restoring the previous resolver on failure). A project opened without a main scene rebuilds the scene left open against its files at once, so a missing atlas shows as a build error then rather than after the next edit. `syncProjectAssets` (`editor/project_assets.go`), called from `syncScenePath`, `Rebuild`, `Assets` and `MoveFile`, retargets the resolver at `ScenePath` and calls `Refresh` whenever `assetsRev` moved (pack install or removal, MoveFile, ReloadAssets, RefreshSearch, which may add, remove or rewrite atlases and materials), and `scene3D` calls it when it sees `assetsRev` move, so the 3D build gets fresh materials. It keys on `assetsRev`, not `filesRev`, because `filesRev` also moves on every scene, clip and table save, which would walk and parse the whole project on each Ctrl+S; `openProject` records the bump it makes itself so the fresh resolver is not walked twice.
- **One command line**: package `editor/editorcmd` holds `New`, `Open`, `Run`, `Main`, `Show` and `ProjectRoot`. `go tool game editor` uses it; a scene file inside a project opens through `OpenProjectScene`, so `ScenePath` is set and self-instancing is refused as a cycle. Without a project the demo editor still opens, with `sceneformat.FSAssets` over the scene's own directory and the demo atlases, as before. `editorcmd.New` checks against a copy of `Options.Components` with the built-in physics components added (a game's own type of the same name wins), since the registry `game generate` starts is empty and a scene with a `body2d` would otherwise not open in the generated editor although it opens free-form in `game editor`. A project without an editor of its own has free-form components, yet `Editor.SetComponentField` still checks the built-in physics components' fields against `sceneformat.PhysicsComponentRegistry` when no registry is set, as the inspector already looked their schema up there (`lookupComponentType`), so `scene_edit` over MCP keeps refusing a misspelled `body2d` field as it did with the demo registry. `ProjectRoot` walks up to the first directory holding game.yaml, nsgo.yaml or go.mod and reports a project only when that one has a game.yaml, the root assetcheck and `refs` find, so a scene in a nested module never opens with an unrelated project further up.
- **A game's own editor is its main package under a build tag**: `game generate editor` writes `editor.go` (`//go:build gameeditor`, a `main` calling `editorcmd.Main` with `Components` and `editorPlugins`) and `editor_test.go`, and adds `!gameeditor` to the constraint of every file that declares the game's `main`, for any platform (`GoFiles` plus `IgnoredGoFiles`, skipping `//go:build ignore` tools), keeping an existing expression (`go/build/constraint`); a failed rewrite puts back the files already rewritten. Because the whole file leaves the editor build, it refuses a main file that also declares a name another file or a test refers to (identifiers outside selectors, so a field called like the helper is no reason), an `init`, a blank `var` or a method on another file's type. `game editor <dir>` detects that tagged main, or a `cmd/editor` main package that imports `editorcmd` (one that does not is reported on stderr and the project opens in `game editor` itself, since it may reject the arguments), and runs it with `go run` in the project directory, forwarding the scene and clip as absolute paths, the object ID as it is, and `-library`. A `cmd/editor` is expected to speak `editorcmd`'s command line; Field Medic's was ported to `editorcmd.Main` with `Options.RequirePlugins`, which keeps its refusal of a project listing a plugin it lacks. `Options.WindowWidth`/`WindowHeight` size the window (default 1120x680), so Field Medic keeps its 1280x800. `editorcmd.Show` serves the editor's MCP endpoint (`editorcmd.Serve`, moved from `cmd/game`'s `serveEditor`), so an agent reaches a game's own editor as it reaches `go tool game editor`.

## Alternatives considered

- **Write `cmd/editor/main.go` that imports the game, as #905 sketched** — it matches Field Medic's layout and keeps the game's main file untouched. Rejected for generated projects because `game new` and `game generate` put `Components` in the root `main` package, which Go cannot import; the editor would have had to move the game's code into a library package first. `game editor` still runs a `cmd/editor` main package when a project has one, so Field Medic's layout keeps working.
- **Start the editor from an `init` in a tagged file and leave main.go alone** — it would avoid rewriting the user's file. Rejected because component registrations also run in `init`, in file-name order, so the editor could start before `Components` was complete.
- **Have `editor.OpenProject` always replace the resolver** — simpler for callers. Rejected because programs and tests that pass their own resolver (Field Medic's `AtlasMap{}`, the editor tests' maps) would silently lose it; `ProjectAssets` keeps it explicit.
- **Re-stat atlas files on every lookup instead of `Refresh`** — would pick up external edits at once. Rejected for now: `Rebuild` runs after every edit and the asset browser lists every frame, so the cost grows with the project; refreshing when the editor changes the project's files covers the pack-install path the issue needs.

## Consequences

- **Benefits**: `game editor` on any project draws its sprites, lists its atlases, places its scene files and opens scenes with unregistered components; a project with `game generate editor` gets its components checked and its plugins built in by the same command.
- **Costs and known limits**: a hand-written `cmd/editor` that does not use `editorcmd` is not run by `game editor`. Atlas names inside instanced and inherited scenes show as root-relative paths in the resolved view. Atlases and materials changed on disk by another program are seen only after a rescan (RefreshSearch, ReloadAssets) or a reopen; tilesets and maps are read again on every `Rebuild`, as `FSAssets` reads them. The generated editor's test runs only with `-tags gameeditor`.

## Verification

- `go tool nsgo test ./project ./editor/... ./tooling/assetcheck ./cmd/game` from `packages/game`: resolver rules, the editor's UI test that the viewport draws the project's image, instancing and cycles, and `TestGeneratedEditorChecksTheProjectsComponents`, which builds a `game new` project's generated editor offline and refuses an undeclared field.
