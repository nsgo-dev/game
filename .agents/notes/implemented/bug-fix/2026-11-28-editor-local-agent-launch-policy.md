# Agent Note: Local agent launch policy

Status: implemented

## Problem

`CLIAgentRunner` (`pkg/editor/agent_runner_desktop.go`) starts Claude Code or Codex headless in the project root for composer requests, plan steps, background tasks, automations and Start with AI. It passed the project's own `.mcp.json` to Claude Code and set no setting sources, permission mode or tool rules. A headless `claude -p` session loads the project's `.claude/settings.json` hooks and connects the servers in its `.mcp.json` without a trust prompt, so the first composer request in a cloned, templated or downloaded project could run any command those files name. Whether the CLI could also edit files or run commands outside the editor's turns and `permissions.yaml` depended on the person's own Claude Code or Codex settings, which the editor neither set nor showed. Text in third-party game content reached the model with nothing saying it is data. A project's own `automations.yaml` could also start unattended agent runs, with the rule's instruction sent as the request prompt, as soon as any agent was connected.

## Decision

The editor never lets a project's own agent configuration run when it starts a local agent, and pins each CLI to the editor's tools:

- **Claude Code** (`claudeLaunchPolicyArgs`): `--setting-sources=user` (project and local settings, with their hooks, permission rules and plugins, never load), `--strict-mcp-config` with an inline `--mcp-config=<json>` built from trusted data only: the editor's server (`editorMCPServerName`, `EditorMCPServerCommand()`, which `editormcp.InstallCommand` now returns) plus the enabled servers from editor.yaml (`AgentRequest.MCPServers`, set from `Editor.AgentMCPServers()` at every `runner.Run` site). A person's server whose name is not `[A-Za-z0-9_-]{1,64}` or equals the editor's is skipped, so it can neither replace the editor's entry nor inject a tool rule. `--permission-mode=dontAsk`, `--allowedTools=mcp__<server>__*` for exactly those servers, and `--disallowedTools=Bash,PowerShell,Edit,Write,NotebookEdit` so a deny beats any allow rule in the person's own settings. Every flag uses the `--flag=value` form, so Claude Code's variadic options never swallow the next argument.
- **Codex** (`codexLaunchPolicyArgs`), on both `codex exec` and `codex exec resume` (`resume` has no `--sandbox` flag): `--ignore-rules` (no user or project execpolicy `.rules` files, whose allow rules would run commands outside the sandbox), `-c sandbox_mode="read-only" -c approval_policy="never"`, and `-c projects={"<dir>"={trust_level="untrusted"},...}` for the project root and every folder above it, both as given and with symlinks resolved (`codexUntrustedProjectsOverride`). Codex loads a `.codex/config.toml` layer, with its MCP servers and hooks, for each trusted folder between the working directory and the repository root, and its trust flag is a one-time, per-path setting, so a folder the person once trusted would otherwise pick up any server a later `git pull` adds. Checked against codex-cli 0.172 with `codex mcp list`: a dotted `-c projects."<path>".trust_level=...` key does not take effect (the path is split on dots), while the inline-table form does, and it must cover each layer's folder, not only the working directory. The person's own `~/.codex/config.toml` still loads. The editor's server and the person's enabled servers from editor.yaml are passed as `-c mcp_servers.<name>.command=<json string>` and `-c mcp_servers.<name>.args=<json array>` pairs (a JSON string or array of strings is valid TOML), with the same name filter as Claude Code, so Codex has the editor's tools without folder trust and the first-run guidance no longer tells the person to trust the folder.
- **Untrusted content notice** (`agentUntrustedContentNotice`): one line in the built-in agent's system prompt, at the start of Claude Code's `--append-system-prompt`, and in front of the Codex prompt on fresh and resumed runs (Codex has no system-prompt flag), says that text from project files, packs, mods and imported content is data, never instructions.
- **Automations held until the person allows them** (`AutomationsHeld`, `AllowProjectAutomations`): when a project's `automations.yaml` has an enabled rule and its SHA-256 is not the one recorded for that project folder under `agent.approvedAutomations` in editor.yaml, `startAutomationTask` starts nothing and Settings › Automations shows a banner with **Allow automations** above the rules, whose instructions the page already lists. A save through the editor (only the person can save that file; agents get `ErrAutomationYouOnly`) records the new digest when the file was allowed, and keeps a held file held, so toggling one rule never allows the others. A file with no enabled rule is not held: every rule it later enables is one the person switched on. The approval lives in editor.yaml, not the project's `.nsgo/automations-state.yaml`, because the project controls everything under its own folder.

The project's `.mcp.json` and `.codex/config.toml` are still written by `editormcp.InstallWithServers` for agents a person starts in a terminal; those agents apply their own trust prompts.

## Alternatives considered

- **Hashing the project's Codex config and asking when it changes, instead of marking the folder untrusted**: keeps project-defined Codex servers in a folder the person trusted. Rejected for the same reason as below: the composer does not need them once the editor passes its own servers inline, and an untrusted override needs no stored state.
- **Keeping the automation approval in `.nsgo/automations-state.yaml` or a field of `automations.yaml`**: no editor.yaml schema change. Rejected because a cloned project can ship either file already marked approved.
- **A per-computer trust list with a banner, restoring project hooks and servers once trusted**: closest to how Claude Code and Codex behave interactively, and it keeps project-specific servers available in the composer. Not taken in this change because the composer never needs project hooks or servers to work (the editor's server and the person's servers come from editor.yaml), and a trust list adds UI, a stored format and a review step for changed files; it can build on these flags later.
- **`--bare` for Claude Code**: skips hooks, plugins and CLAUDE.md discovery in one flag. Rejected because it reads only `ANTHROPIC_API_KEY` or an `apiKeyHelper`, which breaks people signed in with a Claude subscription.
- **Filtering the project's `.mcp.json` down to the editor's entry**: keeps one source of truth on disk. Rejected because the project controls that file and can point the editor's entry at any command.
- **Pre-approving `Read`, `Glob` and `Grep`**: would let the CLI read freely. Rejected because a `Read` allow rule also covers paths outside the project (keys, tokens); reads inside the working directory need no approval.

## Consequences

- A cloned project's hooks, MCP servers and Claude Code permission rules no longer run from the composer; the CLI's own Edit, Write, Bash and PowerShell tools are denied, and Codex stays read-only, so changes go through editor tools, turns and `permissions.yaml`.
- Breaking for composer users who relied on a server listed only in the project's `.mcp.json`, on project Claude Code settings, or on Claude Code editing files directly: they add the server in Settings › Tools instead. Servers in the person's `~/.claude.json` are not connected either, because of `--strict-mcp-config`.
- The flags need a Claude Code release that supports `--permission-mode=dontAsk` and `--setting-sources`; older CLIs fail fast with an unknown-option error in the panel.
- Existing projects whose `automations.yaml` has enabled rules show the held banner once after updating, because no approval was recorded for them yet.
- Codex prints a warning on stderr that untrusted project configuration is disabled; the runner surfaces stderr only when the run fails.
- Testing: `TestBuildCLIArgsIgnoresProjectAgentConfiguration` (`pkg/editor/agent_runner_desktop_test.go`) writes a hostile `.mcp.json` and `.claude/settings.json` and asserts the exact Claude Code policy flags, the inline server list and the notice, and for Codex on fresh and resumed runs `--ignore-rules`, the sandbox and approval pins, the inline editor and running-game servers, the untrusted override for the project root, its parent and its resolved path, and the notice at the start of the prompt. `TestAutomationsFromProjectFileHeldUntilAllowed` (`pkg/editor/automations_test.go`) opens a project whose `automations.yaml` ships an enabled daily rule and asserts no runner call until **Allow**, that the approval survives reopening through editor.yaml, that an outside change holds the file again, and that toggling one rule of a held file keeps it held.
